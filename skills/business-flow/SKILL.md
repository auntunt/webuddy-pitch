# 业务流梳理

toB 老项目里，最难的不是语法，而是“这个按钮背后到底发生了什么”。本技能的产出是一份能拿给开发和业务方看的业务流报告：**工具抽出的事实**在左，**用业务语言写的理解**在右，后者要经人确认。

## 步骤

1. **抽取事实**
   - `tmh map`（若地图不存在或已过期），然后 `tmh flows`，看清有多少条入口、哪些写表、有哪些状态机。
   - `tmh note finding "<一句话>"` 记下第一印象，例如“核心单据是 OA_LEAVE，状态字段 STATUS 有 5 个值”。
2. **挑重点**：优先整理以下流程，其余的可以只保留自动抽取结果：
   - 写核心业务表的（看 `tmh flows` 输出里带 C/U/D 的）
   - 改变状态字段的（状态机里出现的）
   - 定时任务和消息监听（容易被忽视，又常常改数据）
   不确定哪些是核心时，列 5～10 个候选给用户选。
3. **逐条理解**：`tmh flows <id或关键词>` 看调用链、SQL、状态变化、代码中的校验，再打开相关文件核实。
   工具看不到的要自己补：权限判断、前端页面上的约束、存储过程和触发器里的逻辑、配置开关、反射或动态 SQL。
4. **写业务说明**：业务流说明就是知识库的 `flows/<id>.md` 页面。`tmh kb build` 生成页面骨架（上半部分是工具抽取的事实），
   然后 `tmh kb next --page flow:<id>` 领取、按要求用**业务语言**填写下半部分（业务目的、触发与角色、主要步骤、业务规则、状态变化、异常与边界、待确认问题），
   写完 `tmh kb done flow:<id>` 校验入库。要梳理整个系统时改用 `legacy-onboard` 技能，按队列自底向上完成。
   - 不确定的写【推断】，需要业务方回答的写【待确认】。
   - 只有人看过后才用 `tmh kb confirm <id> --by <姓名>` 标“已确认”。智能体不要自己确认。
5. **记录过程**：关键发现、取舍和疑问用 `tmh note finding|decision|question "<一句话>" --detail "<证据>" --flow <id>` 记下，报告的“分析过程”页会按时间展示。
6. **生成报告**：`tmh report`，产出 `.tmh/report/`（index.html + data/，整个文件夹离线可看）。告诉用户文件位置，并说明：
   哪些流程已整理、哪些【待确认】问题需要谁回答、哪些调用工具没能解析（报告里“未能解析”一栏）。

## 注意
- 报告里的事实来自静态分析：反射、动态 SQL、配置驱动的路由、存储过程内部逻辑都可能看不到，要在说明里写明。
- 业务名优先用代码注释，没有就用业务方的叫法；不要编造业务名。
- 说明要短：一条流程一屏以内。细节放证据链接，不要复述代码。
