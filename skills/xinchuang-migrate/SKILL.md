# 执行信创改造

前提：已有 `.tmh/workitems.json`（没有就先用 `xinchuang-assess`）、已建基线（`tmh baseline`，最好 `--with-tests`）。

## 每个工作项的循环

1. **领取**：`tmh items -v` 看清单，按波次和依赖选一项；`tmh items --set <ID> --status doing`。
   同一波次里先做机械性的（驱动、连接串、方言配置、路径配置化），后做语义性的（SQL 改写、存储过程、加密算法替换）。
2. **读知识库**：工作项的 `kb` 字段指向 `.tmh/kb/` 中的章节，先读再改。
3. **写契约**：较大的工作项（L 级、或涉及数据语义）用 `tmh task new "<标题>" --kind migration` 写清改什么、保持什么、怎么验证。
4. **先有测试再改**：
   - SQL 改写：为受影响语句准备特征测试（固定样例数据 → 期望结果），在原库跑通；有目标库测试实例时在目标库再跑。
   - 加密替换：用标准测试向量；存量数据走“双读 + 渐进迁移”，不要一次性转换。
   - 不能修改基线中已有的测试（钩子会拦截），需要时新增测试。
5. **修改**：按命中清单逐个文件改，保持最小改动；不顺手重构无关代码。
   - 可以批量机械替换的，写一个脚本执行并把脚本放进任务目录，便于复现与审查。
   - “兼容模式下可保留”的写法不要改，但在工作项备注写明依据（兼容模式参数、验证结果）。
6. **验证**：`tmh verify`。失败时先读失败原因，修代码而不是改检查。
7. **记账**：`tmh items --set <ID> --status done --note "改了哪些文件/保留了什么/如何验证"`；无法完成的标 `blocked` 并写清卡在哪里、需要谁提供什么。
8. 一批工作项完成后 `tmh assess` 刷新命中数，确认对应规则的命中下降。

## 各类别要点（细节见 .tmh/kb/）
- **数据库**：先确认兼容模式和大小写/字符集参数（需要人决定）；驱动/方言/分页插件 → 主键策略 → SQL 方言 → 存储过程。用 `tmh impact <表名>` 确认每条 SQL 背后的入口，以便回归。
- **中间件**：先“原样部署看报错”，按报错清单改描述符、类加载、JNDI。
- **操作系统/架构**：路径和命令配置化；本地库逐个找目标架构版本，找不到列为阻塞项。
- **国密**：先确认密码应用方案的范围（需要人决定），区分口令/数据/签名/指纹。
- **前端控件**：ActiveX 控件需要厂商信创版本，代码侧只能做接入改造。

## 不要做
- 不要连接生产库、不要执行 DDL/数据迁移脚本，生成脚本交给人执行。
- 不要为了让扫描“清零”而删除功能或注释掉代码。
