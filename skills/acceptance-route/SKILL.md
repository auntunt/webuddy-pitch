# 验收分流与 L1 核对

目的：让每条验收标准在开工前就知道“靠什么证明”，改完后先用读代码和图谱能做的检查挡掉明显问题。
规则见 `docs/acceptance.md`。你可以推进到 `implementing`、`verify_local`、`needs_human`，**不能确认、不能关单**。

## 开工前：分流

1. 读契约第 2–6 节。第 4 节每条 AC 补“层级”列：
   - **L1** 读 diff、契约、图谱就能证明（例：新增 SQL 不含 Oracle 专有写法；没改 `approve` 方法）
   - **L2** 能在独立环境用测试或 `tmh verify` 证明（例：不传参数时 SQL 不含新条件）
   - **L3** 必须在部署后的可测构建上再跑（例：和网关、定时任务、真实中间件有关）
   - **L4** 要真实库、真机或业务判断（例：真实库上筛选条数对得上；报表口径对不对）
   拿不准时往高标。每条写清检查方式：命令、测试名，或人工步骤（数据前提、操作、看什么、找谁确认）。
2. 第 5 节“入口”一行把入口写进反引号（`类名.方法名`、`GET /url` 或业务流 id）。用 `tmh flows <关键词>` 确认它是一条能追到的业务流；追不到的（反射/配置分派）在第 6 节写明，相关 AC 标 L4。
3. 根因写在契约里并带证据（`文件:行号`、日志、复现步骤）；只有推测的写【待确认】，不能当结论。
4. `tmh accept check <任务号>`，全部通过后 `tmh accept advance <任务号> --to implementing`。被拒绝就按提示补，不要绕过。

## 改完后：L1 核对

逐条做，结论写进契约第 8 节：

- [ ] `tmh accept path-check <任务号>`：改动都接上了入口。报“平行实现”说明写了没接上；报“契约外的业务流”说明改到了别处，要么回退，要么在契约里写明并让人确认。
- [ ] `tmh flows --changed` 触及的业务流和契约第 5 节一致，多出来的逐条解释。
- [ ] diff 只做了第 2 节要改变的事，第 3 节必须保持的行为没碰（对照 `git diff`）。
- [ ] 改动规模对得上问题：一处空指针、一个缺接口，不该改出几百行；有无关文件、顺手重构、调试代码就退回。
- [ ] 改了公共方法、工具类、共用组件时，`tmh impact <类名>` 看扇出，把受影响的入口写进契约，必要时给这些入口补 AC。
- [ ] 每条 AC 的检查方式确实能证明它（测试名真的覆盖了这条，而不是别的）。
- [ ] 图谱看不到的改动（前端、配置、字段常量）已在 AC 里对应到 L4 人工步骤。

有问题：`tmh accept reject <任务号> --note "哪条没过、证据在哪"` 退回。没问题：交给 `acceptance-l2` 做独立复验。
