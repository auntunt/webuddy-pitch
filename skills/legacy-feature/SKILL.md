# 老项目新需求实现

老项目里最贵的不是写新代码，而是“改了这里，别处坏了”。本流程的重点是先弄清楚影响范围、先保护旧行为。

## 步骤

1. **建契约**：`tmh task new "<需求标题>" --kind feature --request "<需求原文>"`，打开生成的文件。
2. **理解需求**：把需求改写成“要改变的行为”和“必须保持不变的行为”，每条都要能观察（输入/输出/页面/接口/报表）。
   需求里模糊的地方写进第 6 节问题清单，**影响实现方向的问题先问用户**，不要猜。
3. **定位**（从知识库出发，不要通读代码）：
   - **先运行 `tmh context "<需求原文>"`**：它从知识库和图谱里取出相关的业务域、业务流、业务对象页面和代码位置。先读这些页面，再打开它指出的文件。
   - `tmh flows <id>` 看相关业务流的完整调用链、SQL、状态变化；`tmh kb show <类名|方法|表名>` 看图谱里的调用方、被调用方和读写关系
   - `tmh impact <表名|类名>` 找所有读写方与受影响入口（反向追溯三层）
   - 知识库没有覆盖到的流程，弄清楚后用 `tmh kb next --page flow:<id>` 补写，下次就不用再读
   - 需要大范围阅读时交给 `impact-analyst` 子代理（如可用）
   - 把影响范围写进契约第 5 节，每项附 `文件:行号`；**受影响的业务流**逐条列出（会改变状态流转的要特别标出）
   - 定位结论用 `tmh note finding` 记一笔
4. **定验收方式**：契约第 4 节逐条写出验收条款、层级（L1–L4）和检查方式，用 `acceptance-route` 分流。优先自动化测试；无法自动化的写清人工验证步骤。
   第 5 节“入口”把入口写进反引号。`tmh accept check <任务号>` 通过后 `tmh accept advance <任务号> --to implementing`，**没有完整 AC 不动代码**。
5. **补特征测试**：对“必须保持不变”的行为写测试，先在**未修改的代码**上跑通（证明测试本身正确）。
6. **实现**：遵循项目现有风格（框架、分层、命名、异常处理、日志），最小改动；新增表/字段时给出 DDL 脚本，但不执行。
   改造目标存在时（例如目标库为达梦），新写的 SQL 和代码也要符合目标环境，钩子会提示不兼容写法。
7. **验证**：`tmh verify --task <任务号>`（含入口路径检查：改动必须接上契约入口，另写一套没接上的会失败）；`tmh flows --changed` 看实际改动触及了哪些业务流，和契约第 5 节对比，多出来的要解释；把每条验收条款的结果填回契约第 4 节，未验证的明确写“未验证”及原因。
8. **收尾**：用 `knowledge-upkeep` 增量更新知识库（`tmh kb build` 会指出因本次改动过期的页面，逐个修订）；`tmh report` 重新生成报告；`tmh accept advance <任务号> --to verify_local`，再交给 `acceptance-l2`（或 `independent-verifier` 子代理）独立验收。
9. **汇报**：改了什么、如何验证、还有什么没验证、需要谁做什么（例如执行 DDL、业务验收）。**不要写“已完成/已关闭”**：自测通过、合并都不等于修好，关单只认用户确认，由人用 `tmh accept confirm|close` 或平台“验收通过”操作。
