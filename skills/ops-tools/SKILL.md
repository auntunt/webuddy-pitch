# 运维工具协同

工单、构建、质量、文档都通过 tmh 统一读取，不要自己拼 curl、不要向用户索要 token。
tmh 会把这些外部信息和项目知识库对上：工单 → 相关业务流和代码，构建失败 → 出错的业务流。
有 MCP 工具（`mcp__tmh__*` / tmh 服务）时优先用 MCP；否则用命令行 `python3 .tmh/tool/tmh.py`（下文简写 `tmh`）。

## 先看接了什么
`tmh int list`：已接入的工具、能力、所需环境变量是否已设置。
没接入的能力不要硬做，告诉用户可以用 `tmh int add` 接入（`tmh int types -v` 看各工具需要的配置）。
环境变量缺失时，请用户在启动智能体的终端里 `export 变量名=...`，**不要让用户把凭据发给你，也不要写进任何文件**。

## 按工单开工
1. `tmh ticket <工单号>`（MCP：`ticket`）：工单详情、最近评论、关联单，以及知识库里相关的业务流/表/代码位置。
2. 确认要做后 `tmh ticket <工单号> --task`（MCP：`ticket_task`）：生成带工单链接的任务契约，再按 `legacy-feature` 技能补全契约、实现、验证。
3. 历史上做过相关改动时，`tmh trace <工单号>` 看哪些提交、哪些文件、哪些业务流动过。

## 构建失败
1. `tmh build failure [job]`（MCP：`build_failure`）：最近一次失败构建的错误行、落在本项目代码里的 文件:行号、对应的方法和业务流。
2. 从受影响的业务流出发：`tmh flows <id>`、`tmh context "<错误信息>"`，不要从头读日志或仓库。
3. 只有错误在框架/环境（依赖下载、磁盘、证书、节点离线）时，如实告诉用户是环境问题，不要改代码去“绕过”。
4. `tmh build log [job] --number N --tail 400` 需要更多日志时再看。

## 代码质量与合并请求
- `tmh quality [--severity MAJOR] [--path 目录]`：Sonar 问题按业务流分组，先处理核心业务流上的高等级问题。`tmh quality --gate` 看门禁。
- `tmh change get <!id>`：合并请求的改动文件和涉及的业务流，评审时据此决定要重点核对哪些业务规则。

## 文档
`tmh doc search "<业务词>"`、`tmh doc get <id>`：需求说明、设计、运维手册。文档与代码不一致时以代码为准，并 `tmh note question` 记下差异。
读到的业务规则如果知识库里没有，补进对应知识页（标注来源文档链接）。

## 写操作（评论、流转、触发构建、发通知）
- 默认只演练：命令会打印将要发送的请求，不会真的执行。
- **真正执行前先征得用户同意**，再加 `--confirm`。MCP 里只有仓库配置 `integrations.agent_writes=true` 时 `confirm=true` 才生效，否则请用户在终端执行。
- 评论内容写清：做了什么、改了哪些文件、怎么验证的、还有什么待确认；不要贴大段代码或日志。
- 不触发发布/部署类 job，不流转到“已发布/已关闭”等终态，除非用户明确要求。
