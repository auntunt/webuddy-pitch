## 解读与注意

- cold 的 16 条回答全部是空数组（模型按指令“没把握输出 []”）：cold recall=0 是**拒答**而不是乱猜；有上下文后才有 10/16 条给出答案。这说明上下文解决的是“从 0 到有”，还没有到“找得全”。
- pack-4000 与 pack-8000 的 recall 完全相同：该样例项目知识库很小，4000 字符包已基本包含全部条目，把预算翻到 8000 没有新增信息（同一原因也见 `context-quality-report.md` 的 complete_rate）。
- 延迟不能跨条件直接比较：cold 平均 4.34s 明显高于其他条件（0.90s / 0.90s），而条件按 cold → pack-4000 → pack-8000 顺序执行——第一个条件包含 Ollama 模型加载与首推预热；要看真实推理延迟应固定条件重复测量。
- 上下文代价：prompt tokens 均值 61.5（cold）→ 1262.4（pack），约 20.5x；completion tokens 含全部推理 token。
- 样本只有 16 条、单个 9B 模型、单次 temperature=0 运行：结论只作方向性参考，不构成统计显著性。

## 口径说明
- 找全率：gold 文件被模型答案覆盖的比例（文件级 recall），解析失败/空答按 0 计，不从分母剔除。
- exact：只有 gold 文件全部被找到才算对（文件级准确率）。
- 真实 completion tokens：Ollama 返回的 `eval_count`，包含推理 token；有效输出 tokens 用 `estimate_tokens` 估算模型可见答案。
- 失败分类：`request_timeout` / `request_unavailable` / `request_http_*` / `parse` / `empty` 分别计数。
- 延迟：条件固定按 cold → pack-4000 → pack-8000 顺序执行，第一个条件包含 Ollama 模型加载/预热，不用于跨条件比较。
