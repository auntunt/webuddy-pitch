# 端到端运行记录：全项目分析与增量维护

- 日期：2026-10-07
- 引擎：Claude Code 2.1.292，非交互模式（`claude -p`）
- 对象：`examples/legacy-java-oa`，含请假、报销（含部门预算）、用户三个业务域，共 12 个入口、8 张表、25 个源文件
- 安装方式：`tmh install`，然后 `tmh baseline`

## 第一轮：全项目分析

提示词：

> 请对整个项目做一次统一分析，建立项目知识库……按 legacy-onboard 技能完成……业务流和业务对象页面可以并行派 kb-writer 子代理去写，业务域和总览由你来写……最后生成报告。

| 项目 | 结果 |
|---|---|
| 用时 | 约 3 分 40 秒（以 activity.jsonl 首尾时间为准） |
| 费用 | $1.39 |
| 主会话 | 72 次工具调用，并行派出 3 个 kb-writer 子代理 |
| 产出 | 21 页全部写完并通过 `kb done` 校验：总览 1、业务域 3、业务流 10、业务对象 6、模块 1。另有术语表、坑、待确认问题（20 多条） |
| 投入的上下文 | 约 6 万字符（`kb status` 统计的上下文包总量） |

过程：

1. `kb build`。
2. 记一条第一印象。
3. 3 个子代理用 w1/w2/w3 并行领取业务流和业务对象任务。
4. 主会话等它们写完，再写 3 个业务域页和总览页。
5. 抽查 `ExpenseService` 等处，核对页面写的行号。
6. 生成报告。

智能体从知识库整理出的主要发现（详见 [e2e-knowledge-base/index.md](e2e-knowledge-base/index.md) 和 [pitfalls.md](e2e-knowledge-base/pitfalls.md)）：

- **审批日志表列名对不上**：建表用的是 `BILL_ID`，插入语句用的是 `LEAVE_ID`。按建表脚本建库，所有写日志的流程都会失败。另外报销单号也存进了这一列，表里没有单据类型列。
- **预算按“系统当前月份”匹配**：跨月提交、驳回、付款时会落到错误的月份行。
- **重复驳回会重复释放冻结预算**。
- **出纳付款在本地事务里调用外部支付接口**，而且发生在落库之前。失败时无法回滚已付的款，重试可能重复付款。
- **夜间导出任务实际只写了 "ok"**，还依赖 Windows 的 cmd 和共享盘路径。

发现的问题和修正：

- **主会话没有替换模板，而是在后面追加**：主会话写业务域和总览页时，把内容追加在模板骨架后面，导致二级标题重复。旧版校验只看最后一次出现的标题，所以放过了。
  - 已修正：`kb done` 现在会拒绝重复的二级标题和残留的模板提示，写作要求里也写明“替换提示，不要另起一套标题”。
  - 补了测试 `test_appended_sections_with_skeleton_left_are_rejected`。
  - 本记录里的页面已去掉残留骨架。
- **子代理写术语表时出现了近义重复**：例如“冻结额”和“冻结预算”。这类重复不影响使用，留给人工确认时合并。

## 第二轮：改一处代码后的增量维护

模拟合入一个提交：报销驳回时检查更新行数，0 行就抛异常，不再重复释放预算。

改动后，`tmh kb build` 的结果：

- 只重新解析了改动的文件。
- 报告“1 个知识页过期：flow:post-expense-audit”。
- 同一个类里的“出纳付款”、“提交报销”页面不受影响。
- 修订任务的上下文包同时列出了“其他提到这些代码的知识页”（业务域页等）。

提示词：

> 刚合入了一个提交（修复：重复驳回不再重复释放预算）。请按 knowledge-upkeep 技能增量更新项目知识库，只修订受影响的页面。

| 项目 | 结果 |
|---|---|
| 用时 | 56 秒 |
| 费用 | $0.27 |
| 对话轮数 | 16 轮 |
| 改动的页面 | 财务审核业务流页（修订后回到“待确认”）、业务域页、`pitfalls.md`、`open-questions.md`，共 4 个页面、19 行增加、22 行删除。其余 17 页没动 |

修订示例（`pitfalls.md`）：

```diff
-- 报销驳回不校验单据当前状态却无条件释放预算，重复调用会多释放（ExpenseService.java:62-67）。
+- 报销重复驳回已修复：驳回更新 0 行即抛异常，不再重复释放预算（ExpenseService.java:64-68）。遗留：重复“通过”不检查影响行数，仍会写 EXPENSE_PASS 日志（ExpenseService.java:61-62）【推断】。
```

结束前 Stop 钩子要求先运行 `tmh verify`，因为代码相对基线有改动。验证通过：`mvn test` 退出码为 0。

## 结论与局限

- 全项目分析的成本，主要取决于纳入范围的页面数。这个样例 21 页花了 $1.39。按页估算，几百页的项目在几十美元量级。日常维护只为变化付费：这次改一个方法花了 $0.27，而重新分析全项目要花 $1.39。
- 这次用的是 Claude Code 和 Claude 模型。Codex 以及 Kimi/GLM/DeepSeek 下还没有跑过。子代理和钩子的配置已经按 Codex 的格式生成（`.codex/agents/kb-writer.toml`、`.codex/hooks.json`）。
- 样例项目很小。真实的几十万行项目上，业务域划分的准确度、上下文包的预算是否合适，还需要实测。
