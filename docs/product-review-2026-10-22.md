# Webuddy 产品逻辑复核与下一步建议

> 历史审查记录：用户随后明确优先交互、知识与团队协作，已进入实现；本轮最终范围见 [工作区设计与实现](design/workspace-2026-10-22/README.md)。下文建议保留原样作为决策背景。

日期：2026-10-22。审查基线：`30686e6d3a8d2d3aaefe490cfc456e55c00f46f3`。

本轮核对产品定义、当前后端与网页代码、已有测试，以及本地业务验收和生产发布记录。没有重新登录生产、调用业务模型或运行真实客户任务；已有测试是实现依据，不作为本轮新执行结果。本文件是产品建议，未将建议改成产品功能或已确认需求。

**结论：核心能力已覆盖多数环节，当前主要欠缺跨入口一致的状态、明确的责任交接，以及从验收到实际交付和收益衡量的衔接。下一轮应围绕一个真实需求完成整条路径。**

## 产品应让谁获得什么

[PRODUCT.md](../PRODUCT.md) 的全周期目标继续保留。建议下一阶段的主要使用者明确为：**已有项目、需要对交付负责的开发者或技术负责人**。客户提供业务规则并确认结果；开发者及编程助手执行；项目负责人掌握阻塞、版本和交付依据。

首条验证路径建议选择已有仓库中的一条真实缺陷或小功能。这个选择是验证顺序，不删除新建应用、调研、设计、迁移和重构等能力。Coding 仍独立；办公软件同步不成为本轮前提。

产品需要持续回答五个问题：

1. 现在处理哪件事，为什么值得处理？
2. 当前做到哪一步，接下来谁执行什么动作？
3. 结果依据哪个需求、代码版本和验证记录？
4. 验收后的成果在哪里可用，交给了谁？
5. 实际投入多少时间和费用，后续是否返工？

## 已有基础与验证边界

| 环节 | 已有能力 | 本轮判断 |
|---|---|---|
| 需求澄清 | 保留原话、拆分需求、客户答复、确认验收条件、条件变化后重新确认 | 应复用，不再另建需求系统 |
| 项目知识 | 知识图谱、人工确认、过期检测、按任务组装上下文及来源回执 | 应在真实任务中测相关性和维护成本 |
| 执行 | 内部 Agent、外部 CLI/MCP、独立工作树、有限返工、整次执行期限 | 已有机制，仍需跨项目复用验证 |
| 恢复 | 保留旧运行和改动、核对停止回执、新运行接续、保存客户答复后重试理解 | 已有，不把“加恢复按钮”当新需求 |
| 质量与签收 | 独立验证、固定候选、预览、逐项技术观察、证据绑定、客户签收 | 各路径能力不同，需统一呈现与语义 |
| 发布与反馈 | 本地合并/标签、版本页、预览分享、经验卡、基线与提效报告 | 需要补交付环境回执及新路径统计 |

不能说“尚无真实业务实践”：历史记录包含 BOOTV2 的真实模型执行及用户本地验收，也包含磅单候选的真实代码和浏览器技术验证。磅单当时仍待业务确认，使用隔离合成数据。2026-10-21 的生产升级验证了运行、读取和数据保全，没有完成生产业务工单及模型调用。三个事实分别记录，不能互相替代。

依据：[历史实用性评估](self-improvement/usability-assessment-2026-10-19.md)、[业务实践记录](self-improvement/STATUS.md)、[生产发布验证](../audit/production-deployment-2026-10-21.md)。

## 优先处理的六项

优先级是实施建议：“第一批”服务第一条可靠交付路径；“随首单记录”要求立即收集数据，不等仪表盘开发完；多人能力在扩大团队试点前补齐。

| 顺序 | 要解决的产品问题 | 当前性质 | 最小交付 |
|---|---|---|---|
| 1 | 不同入口对“验收完成”的含义不一致 | 已有行为需要统一 | 按任务类型明确完成条件，内部验收保留逐项结果或明确的人工完成依据 |
| 2 | 换个入口后看不清当前进度和下一步 | 已实现但接线不全 | 交付阶段和外部候选接入工单及“今天”的状态与待办 |
| 3 | 登记项目后不确定到底能不能执行 | 接入体验与验证语义缺口 | 项目接入回执，区分已配置、未验证、实跑通过和失败 |
| 4 | 验收后无法持续追踪客户环境是否已更新 | 环境交付记录缺失 | 固定版本、交付对象/环境、负责人、部署回执和上线检查 |
| 5 | 多人都看到“等你处理”，交接责任不清 | 团队流程未接完整 | 下一动作与责任人，“我的/未指派/团队”待办 |
| 6 | 新交付路径及真实投入未进入价值统计 | 统计口径缺口 | 分开统计关单、有效候选验收、环境交付；记录人工时间与实际/未知费用 |

### 1. 统一完成条件，保留不同任务类型

**观察。** 普通工单的内部验收接口只接收总结果和备注。内部通过时，证据包中的所有验收条件会被写成 `pass`，没有收集逐项结果。普通无证据包的工单也可关单。客户签收页则要求逐项确认，外部候选另有固定版本与证据检查。

**用户影响。** 项目负责人难以区分“负责人确认结束”“逐项业务验证通过”和“完整代码交付已验收”。这些结果会继续影响关单、经验回流和指标。

**最小改动。** 给代码交付、人工运维处理、文档/阶段产物分别定义完成条件。代码交付在内部界面复用逐项确认和当前证据绑定；人工非代码任务可以明确结束，但记录理由、依据和未验证项，不生成并未逐项确认的通过记录。避免把所有任务都强行要求代码 diff 或自动测试。

**完成标准。** 缺失的逐项判断不会被自动补成通过；需求或版本变化后旧决定无效；合法人工处理仍可结束；已关闭历史完整保留并说明其验收口径。

**依据与反证。** [内部验收接口](../tmh/platform/server.py#L1756)、[证据写入](../tmh/platform/signoff.py#L1004)、[既有普通关单测试](../tests/test_platform.py#L1858)。客户页有[逐项确认](../tmh/platform/signoff.py#L619)；交付绑定另有[空包与陈旧版本防护测试](../tests/test_signoff_delivery_binding.py#L157)。因此本项不等于“全平台可以绕过所有验证”。

### 2. 让所有入口反映同一个当前事实

**观察。** 外部候选已有独立验证、预览、技术验收和人工决定，Agent 任务包也能读到它们；普通工单响应没有返回完整候选信息，网页常规提示仍是“等待助手明确启动下一步”。另一个断点是交付流程的非实现阶段以 `ask` 运行，而“今天”的当前运行查询排除了 `ask`；交付产物等待采集、等待复核也未形成统一待办。

**用户影响。** 开发者在 Codex 完成了工作，负责人回网页却不知道接下来做什么；在交付页启动设计后切到“今天”，总览不能完整反映正在发生的事。

**最小改动。** 从现有后端状态生成共享的展示信息：当前需求、产物/候选版本、运行、缺项、下一动作及责任人。工单增加当前候选卡，“今天”纳入交付阶段运行、产物待采集和待复核。优先复用后端接口，不另建一套候选或验收状态机。初版可明确提示最终候选决定通过操作者 CLI 完成；以后加入网页操作仍复用同一人工权限与证据检查。

**完成标准。** 同一任务在工单、交付页、今天和 CLI 展示一致的事实；外部候选提交后可从网页进入；旧证据失效后各入口及时呈现；刷新不丢草稿；读取状态不会触发执行、签收或合并。

**依据与反证。** [普通工单响应](../tmh/platform/server.py#L2030)、[Agent 任务包](../tmh/platform/agent_api.py#L365)、[网页交接提示](../tmh/platform/ui.py#L465)、[今天的查询](../tmh/platform/workbench.py#L927)、[交付运行](../tmh/platform/delivery.py#L581)。[交付页的下一步判断](../tmh/platform/ui_delivery.py#L93)和[候选验收](../tmh/platform/candidates.py#L325)已经存在，应接通它们。

### 3. 把项目登记推进到首次可执行验证

**观察。** 现有接入表单要求“本机绝对路径”，实际在 Webuddy 服务机器上检查。远程网页用户容易把自己电脑的目录填进去。体检对配置中的自定义检查命令直接返回 `ok`，自动识别也主要核对命令及可执行文件；模型没有历史运行时只是警告。没有阻断项时总体提示“可以开始试点”。

**用户影响。** 用户已经填完表单，却要在启动任务后才发现源代码机器、模型登录或构建环境不匹配。配置存在与实跑成功没有明确区分。

**最小改动。** 明确源码位于哪台机器、由哪里执行。登记后展示项目接入回执：固定提交、执行方式、构建/测试命令、数据准备、预览方式和缺项负责人。沿用体检，增加“已配置/未验证/最近实跑通过/失败”的状态、时间和对应回执。用户明确启动首次验证后才执行项目命令；登记项目不自动运行来源脚本。

**完成标准。** 一个未参与搭建的开发者能按界面完成首次验证；每个“实跑通过”都有可打开的回执及适用版本/配置；配置变化或失败后不沿用旧通过结论；缺项给出具体补救动作。

**依据与反证。** [登记表单](../tmh/platform/ui_library.py#L139)、[服务端路径检查](../tmh/platform/server.py#L969)、[构建体检](../tmh/platform/readiness.py#L144)、[总体结论](../tmh/platform/readiness.py#L218)。体检已经识别登录错误、连续失败等情况；新建 Web 起点也已有[创建回执](../tmh/platform/ui_delivery.py#L89)，不能概括为“完全没有接入验证”。

### 4. 补上验收之后的环境交付记录

**观察。** 当前发布模块做本地合并、标签和版本记录，明确不推送、不部署。版本页有预览与分享。交付流程也明确产物复核不代表部署完成。这些边界正确，但还缺结构化的目标环境部署、实际运行版本和上线检查回执。

**用户影响。** 客户问“验收的版本现在在哪里使用”，负责人仍需到平台外追查部署和通知记录。

**最小改动。** 增加交付记录：交付对象是代码/安装包还是运行环境，关联提交与产物、目标环境/入口、负责人、实际执行回执、检查结果和回退依据。先支持人工登记或导入既有 CI 回执。代码交付与运行环境交付使用各自完成条件，不把自动部署作为前提。

**完成标准。** 对需要上线的任务，工单能追到目标环境实际版本和检查结果；失败部署不变成“环境已更新”；旧版本、失败和回退历史保留。只有代码交付约定的任务，不强制要求生产环境。

**依据。** [发布模块边界](../tmh/platform/release.py#L1)、[版本界面](../tmh/platform/ui_work.py#L242)、[全周期交付阶段](../tmh/platform/delivery.py#L28)。Webuddy 自身刚完成的生产升级是运维执行结果，不能据此声称平台已提供通用部署产品能力。

### 5. 让待办交到具体的人

**观察。** 当前 `inbox` 不接收登录用户，按项目工单状态生成 `mine`；“等你验收”并不等于这位登录者被指定为验收人。已有经办人、手工认领、客户签收人和链接过期提示。

**用户影响。** 开发、复核、业务验收、发布之间的责任容易含混，同一项目成员都可能认为对方会处理。

**最小改动。** 增加下一动作及责任人的交接记录。先支持实现、复核、验收、交付四类动作，将待办分为“我的/未指派/团队”；允许改派及说明原因，保留历史。没有负责人时仍在未指派队列中显示。

**完成标准。** A 完成实现交给 B 后，B 得到待办，A 看见等待 B；退回后责任明确回到执行方；已完成动作不会重复提醒；未经指派的事项不会从总览消失。

**依据。** [待办查询及分组](../tmh/platform/server.py#L217)、[接口未传用户](../tmh/platform/server.py#L1524)、[现有经办人字段](../tmh/platform/store.py#L30)。

**多人推广前的另一条件。** 任务指派不等于权限。当前账号和操作者凭据已存在，但还需明确项目成员对查看、执行、复核、签收和交付的权限及撤销。此项在多团队/多客户共用前完成；个人监督试用可保持明确的可信工作区边界。依据：[账号模型](../tmh/platform/login.py#L66)、[操作者边界说明](../tmh/platform/operator_access.py#L1)及[已有组织使用评估](self-improvement/usability-assessment-2026-10-19.md)。

### 6. 从第一单开始记录有效交付和实际投入

**观察。** 提效报告主要按旧工单 `accept` 事件算完成，外部候选决定另存 `candidate_decisions`。同一候选可能多次确认，不能按记录条数算多次交付，也不能为凑统计而自动关单。当前成本账使用按动作固定的演示点数，成功运行后扣点；人工记录是动作次数。部分模型日志有美元/token 信息，但尚未形成跨所有尝试的可靠实际成本账。

**用户影响。** 产品无法完整回答“完成了几项当前有效的交付，人工究竟省了多少，失败尝试用了多少资源”。

**最小改动。** 并列统计已关闭工单、按当前版本验收的唯一交付、已更新环境，不强行合成一个完成率。试点即记录人工分钟、所有尝试及失败原因、实际费用或费用未知原因。演示点数、外部模型费用和订阅分摊分别展示；明确来源后再实现任务费用预算。

**完成标准。** 同候选重复确认不重复计数；旧确认失效可见；失败、放弃、人工补救进入试点分母；人工动作不当工时，点数不当模型账单；没有封存基线仍不出提效对比。

**依据与反证。** [现有统计口径](../tmh/platform/metrics.py#L152)、[人工动作与计价](../tmh/platform/metrics.py#L292)、[候选决定](../tmh/platform/candidates.py#L369)、[固定点数](../tmh/platform/server.py#L121)、[成功扣点](../tmh/platform/agents.py#L1201)。已有[基线封存](../tmh/platform/books.py#L1)和实付未知处理应保留，不需要另起一套仪表盘。

## 建议实施顺序与验收场景

**第一批：让负责人能从网页接住一条真实交付。** 完成条件明确；外部候选、交付阶段接入统一状态与下一动作；为该试点项目补齐可执行回执。人工时间、失败和费用从这时开始记录。

**第二批：让交接一直延伸到约定交付对象。** 增加下一动作责任人及交付记录。如果约定上线，核对目标环境实际版本；如果约定代码/安装包，核对接收对象和产物。保留已有人工决策边界。

**第三批：验证能否复用。** 在第二个真实业务或技术栈重复，不重复同一个演示。扩大到多人之前补项目权限；有足够同口径样本后再展示比较。组织知识/习惯面板、检索算法升级和更多连接器，由实际任务阻塞来决定顺序。

建议用以下场景验收第一批产品改进；它们是验收设计，尚未执行：

| 场景 | 用户可观察的通过标准 |
|---|---|
| 已有项目登记 | 用户能辨认源码机器、执行方式和未验证项，知道下一步找谁 |
| 设计阶段在运行 | 切到“今天”仍能看到任务及入口；产物完成后转为采集/复核待办 |
| 外部助手提交候选 | 网页显示同一 SHA、测试/预览/验收状态和缺项 |
| 只有总体验收，缺逐项结果 | 不自动生成逐项实测通过；人工非代码完成有独立依据 |
| 修改需求或重验后 | 旧确认失效，各入口展示一致，不把历史确认当当前通过 |
| A 交给 B、B 退回 | 下一动作、责任人和双方待办同步，交接留痕 |
| 约定上线但部署失败 | 验收历史保留，环境交付仍失败/待处理，不报已交付 |
| 重复确认及失败重试 | 当前唯一交付不重复计数；全部尝试和人工补救保留 |

本轮没有承诺上线日期或收益比例。判断下一轮成功的依据是以上路径能否被真实使用者完整走通，而不是增加了多少页面、Agent 或测试数量。
