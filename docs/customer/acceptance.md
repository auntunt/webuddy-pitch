# 验证与人工验收

先记录要改变的行为、必须保持的约束、影响范围和逐条验收标准，再开始实现。验收标准缺失或业务规则未确定时，返回具体阻塞及下一责任人。

| 层级 | 依据 |
|---|---|
| L1 | 契约、差异、业务流入口与影响范围核对 |
| L2 | 独立环境复验、用例结果与入口路径证据 |
| L3 | 当前集成版本的系统与环境验证 |
| L4 | 业务负责人在获准入口作出业务决定 |

测试未运行、环境缺失和结果未知不能显示为通过。证据绑定当前代码、验收标准、测试配置及目标环境；相关输入变化后重新核对。历史证据及签收原文保留，历史通过不代替当前有效性。

Agent 可记录检查、报告阻塞和推进允许状态；不能冒充业务负责人、代人 confirm/close、伪造 human 标签、削弱断言或绕过钩子。已有按项目明确启用的平台 AI 验收策略保持原范围；发行包不自动启用或扩大该策略。

使用 `.tmh/docs/agent-commands.md` 中的 task、verify、flows、accept 命令。`accept confirm` 和 `accept close` 仍由现有可信人工入口执行。构建成功、CI 成功和子单关闭不自动代表整体业务交付。

## 本地任务契约

任务原文保存在 `.tmh/tasks/T###-*.md`，验收状态与历史保存在 `.tmh/acceptance/`。契约第 4 节每条标准应包括编号、条款、层级（L1–L4）、检查方式和结果；第 5 节的“入口”使用反引号标明真实入口或业务流 ID。未完成验证时结果写“未验证”，不预填通过。

旧契约缺少层级列时，补列后逐项填写，不降低原来的业务要求。入口不明确时补真实入口，再执行 `accept check`、`accept path-check` 与 `verify --task`。图谱无法证明的反射、动态 SQL 等路径须说明阻塞，不能假定已接入。

常见顺序为 `draft_contract → implementing → verify_local → merged → deployed_awaiting_verify`，随后根据实际证据进入 `auto_verified` 或 `awaiting_business`。证据不足可进入 `needs_human` 或 `blocked`，写明原因后退回实现复验。已合并和已部署分别登记真实 ref/build，登记本身不证明操作或测试已成功。

CLI 的逐项机器证据当前支持 L2 用例映射；L1/L3 使用平台候选、独立复核及部署回执，不接受手写结果替代。测试零条、仅构建、证据身份变化、原始用例文件缺失均不能算通过。`verify-latest.json` 只用于定位，实际引用带 UUID 的报告及摘要，并绑定任务、完整 HEAD、工作区文件字节、基线、配置与契约。

`accept confirm` 必须由有权的人在可信入口执行，`closed` 只能从 `user_confirmed_fix` 进入。实现 Agent 不执行这两步。返修要记录原因并重新形成证据；历史签收不会因新代码或新测试而自动变成当前有效。
