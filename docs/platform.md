# tmh 运维平台（`tmh serve`）

tmh 平台是和 Jira、禅道同级的运维工单平台，面向长期维护的老业务系统。它和通用工单系统的区别在两点：

1. **工单直接连着业务知识库。** 新建工单时，边写描述边列出可能相关的业务流和表；工单页右侧是相关业务流、表、知识页和代码位置，可以一键关联。每条业务流也能反查关联过的工单。
2. **内置 Claude Code 和 Codex。** 在工单上点“分析定位”“修改方案”“修改代码”，平台把工单、讨论、之前的结论和知识库里的相关业务一起交给智能体，过程实时显示，结论记在工单上。

## 启动

```sh
cd /path/to/legacy-project          # 已经运行过 tmh kb build 的项目
python3 .tmh/tool/tmh.py serve --key TOG --open
```

- 默认只在本机 `http://127.0.0.1:8790/` 提供服务；数据在 `~/.tmh/platform/`（`--data` 可改），工单、讨论和运行记录都在其中的 `platform.db`。
- 当前目录有 `.tmh/` 时自动登记为项目；其他项目在网页“添加项目”里填目录即可。一个平台可以管多个项目。
- 给团队用：`TMH_TOKEN=<随机串> tmh serve --host 0.0.0.0`，同事用 `http://<你的机器>:8790/?token=<随机串>` 打开。没有令牌时拒绝对外开放。

## 三层结构

平台分三层，上层只通过下层公开的接口用它，测试里有一条专门检查层与层之间的引用（`test_three_layers_only_meet_at_their_interfaces`）。

| 层 | 管什么 | 代码 |
|---|---|---|
| 知识层 | 项目是什么：业务域、业务流、表、入口和代码证据，知识库页面，图谱和架构图的数据。不知道有哪些应用 | `tmh/platform/knowledge.py`（底下是 `tmh/kb.py`、`tmh/graph.py` 等） |
| 编排层 | 怎么把一件事改对：受理时关联业务流，智能体定位、起草方案、按文件改、构建测试、诊断、提交到独立分支、等验收；验收不通过自动重改；验收结果变成教训和评测用例。不知道有哪些应用 | `tmh/platform/orchestra.py`、`agents.py`、`fixloop.py`、`learn.py` |
| 应用层 | 任务从哪来、谁验收、算什么数。现在有运维服务（报单、导入、助手会话、告警）和重构服务（改造计划） | `tmh/platform/apps.py`（登记）、`reform.py`、`alerts.py`、`server.py` 的接口和 `ui.py` 的页面 |

应用能用的编排层接口只有这些：`submit`（放一个任务上线）、`accepted`（人的验收结论，验收接口调用它）、`take_over` / `resume` / `next_step` / `catch_up`（人接手和交回）、`listen`（听每一次验收结论：`fn(项目, 工单, {passed, note, by, redo, gave_up})`，`gave_up` 写明为什么不会自动重改）、`agent()`（现在会用哪个智能体）、`BY`（自动流程写事件用的名字）。知识层对上提供 `related`、`kb_overview`、`atlas`、`kb_tree`、`kb_page`、`arch` 等读取接口和 `forget`（知识库变了，丢掉缓存）。

以后加工单获取、会议纪要、报价这类服务，是在 `apps.py` 里登记一项、写它自己的模块，知识层和编排层不用改。

## 页面

浅色页面、深蓝顶栏，上面不出现 tmh 字样。顶栏的名字用 `--brand "OA 闭环监控"`（或环境变量 `TMH_BRAND`）设置，不设时是“Webuddy”。

平台分**运维服务**和**重构服务**两套，顶栏中间切换，各有自己的导航；重构服务的顶栏是深紫色，一眼能分清。两套共用一个底座：项目图谱、知识库、架构与依据、智能体运行、设置在两边都有（导航右侧“共用”之后），自动处理流程（分析、改代码、构建测试、等验收、退回重改、教训）也是同一套。改造计划放出的工单只出现在重构服务里：工单看板、工单列表、运维成效、提效报告都不算它们（接口 `GET /api/tickets?svc=ops|reform`）。打开一张改造工单，顶栏自动切到重构服务。

| 页面 | 内容 |
|---|---|
| 工单看板（首页） | 四个完成率仪表（闭环完成率、智能体分析覆盖、代码改动采纳率、知识库覆盖），流转中、失败、已关闭三个数，一行按事实生成的“智能洞察”；下面是六个状态节点组成的闭环圆环，点节点的数字列出那一步的工单。可切到“列表看板”拖卡片改状态 |
| 工单列表 | 按状态、关键词、指派给我筛选 |
| 运维成效 | 给管理者看的，全部项目合计。首屏四个数：响应时长（报单到第一次有人回应）、解决时长（报单到闭环）、一次解决率（验收一次通过）、积压（超过 3 天未闭环），各自对比上一期。下面是“本期做成了什么”（每张闭环单一行：谁报的、根因、谁解决、用时）、团队（解决数、平均解决时长、被退回次数）、智能体分担了什么（只列可数的事实，没启用的功能写“未启用”）、积压清单、每周新建与闭环、各项目对比。全部来自工单动态和运行记录，不做估算 |
| 项目图谱 | 深色画布上逐层看整个项目：**全景**里每个业务域是一个圆（大小按业务流数），表围着它最常用的域转，金色虚线连起共用表的两个域；双击业务域看**业务域**（左边业务流卡片，右边表，黄线写入、青线读取）；双击业务流看**代码链路**（自上而下：入口、各层步骤、读写的表和外部调用，在办工单挂在入口旁）。悬停或选中一个节点时只亮出相关的连线，右侧是它的知识页摘要和在办工单。按 `/` 搜业务域、业务流和表；“讲解”按业务流一步步走（← → 翻页，Esc 退出）；“只看有工单的”只留下在办工单碰到的部分。全部自己画（SVG），不加载外部库，内网也能用 |
| 改造计划（重构服务） | 首屏四个数：改造计划数（几个暂停）、业务域块已闭环 / 总数、待验收、一次验收通过率。下面是老项目的结构重构、依赖升级、框架迁移、兼容适配和跨语言重写（写明目标目录，原代码只读，验收看构建和接口规范测试）。可以带一个先导部分（第 0 部分，比如重写时的工程骨架）：先只放出它，验收通过后记下它最后的提交，其余各部分的改动都从这个提交开始，不动项目自己的分支。新建改造计划时选类型、写目标和不能变的东西、选业务域，下方预览按牵连从少到多排好的拆分；建好后由人点“放出第一批（试点）”，之后每批全部验收通过就自动放下一批，有一块重改后仍不通过就暂停。每个计划一条进度（闭环 / 待验收 / 已放出），展开看每个业务域的工单和状态。升级、迁移时可以看项目当前依赖清单。见下面“重构升级” |
| 改造工单（重构服务） | 改造计划放出的全部工单，按计划和顺序排：计划、第几部分、业务域、状态、退回次数、负责人。可以按计划筛、只看未关闭 |
| 依赖清单（重构服务） | 项目声明的依赖和版本（Maven、npm、NuGet、pip），可筛选。写升级、迁移目标时对照 |
| 闭环改进 | 系统怎么从结果里学：评测集回放（每次的找全率、准确率，展开看每个用例漏了哪些文件、多列了哪些）、用例清单（验收入库的、历史工单生成的和手动加的）、以往的教训、告警自动开单（接入地址、是否就绪、可直接贴告警或报错日志开单、告警开过的单）。见下面“闭环改进” |
| 工单详情 | 两个标签。**工单详情**：标题下一行是项目、状态、类型、优先级、经办人，点一下就地修改；流程条（受理 → 分析定位 → 修改方案 → 修改代码 → 人工验收 → 闭环）每步写谁、什么结果，卡住时写原因。下面一张结论卡固定几行：现象、根因、方案、证据（核实 / 推断 / 代码几处，可展开完整结论）、等谁，后面紧跟当前该按的按钮（待验证时就是验收框）。动态里机器做的连续几步合成一行“自动处理 · N 步”，可以只看讨论或只看自动记录。右侧是可能重复的工单、代码改动、相关业务（已关联的、智能体建议待确认的、其他可能相关的）。手动指派智能体和运行日志收在“执行记录与手动运行”里。**提示词**：见下面“提示词标签页” |
| 监控总览 | 近 14 天新建与关闭、优先级分布、知识库规模、最近运行 |
| 提效报告 | 按月看工单周期、首次定位耗时、验收退回率、AI 参与率、每单 AI 成本，和导入的历史工单（基线）对比；可导出《AI 提效报告》。见下面“提效报告” |
| 知识库 | 三个标签：**知识内容**（左边按业务域列目录，右边阅读；代码证据默认折叠）、**待确认与更新**（待人工确认的页、代码变了需要更新的页；确认时可写备注，记下确认人和时间）、**建设进度**（带分母和更新时间的统计，以及“全项目分析”）。页面状态只有五种：未分析、仅事实、待确认、已确认、需更新 |
| 架构与依据 | 从总览到业务域到业务流：结构图里的入口、业务域、表和外部调用都来自代码解析，标“代码事实”；部署结构代码里没有，不画。点业务域看每条业务流的入口、处理方法、数据操作和 `文件:行号` |
| 智能体运行 | 按“进行中 / 有异常 / 全部”筛选；“来源”一栏写明是哪个会话、工单或知识库批次，不把 `dom:`、`flow:` 当工单号；知识库建设按批次合并显示，可以只重试失败的子任务。执行完成和人工确认、改动采纳分开显示 |
| 外部系统 | 已接入的 Jira、禅道等 |

顶栏的项目选择：工单看板、工单列表、运维成效默认是“全部项目”，可以收窄到一个项目；知识库、架构等属于某个代码库的页面跟随你最近打开的工单或选择的项目。新建工单时在弹窗里选项目。

工单状态：已提交 → 分析中 → 待确认 → 处理中 → 待验证 → 已闭环。智能体会自动推进到“待验证”（见下面“自动流转”）；从“待验证”到“已闭环”只能由人在工单详情里点“验收通过”，验收不通过必须写说明，工单退回“处理中”。

### 维护助手

页面右侧的抽屉（窄屏时从右下角“维护助手”打开）。助手按**会话**组织，每个会话有自己的消息、没发出去的草稿和模型上下文，互不串：

- 抽屉顶部是当前会话：名称、项目、所属工单；可以新建、重命名、归档。归档只是收起来，不删消息、不停正在跑的回答，随时能恢复，归档的会话不能继续发送。
- “历史”按 项目咨询 / 关联工单 / 已归档 分组（以前建的维护事项会话归在项目咨询里），可按标题搜索。
- 切换页面不换会话。打开另一张工单时，抽屉顶部会问“进入该工单会话 / 保留当前会话”，不会悄悄改绑。
- 会话是个人的：只看得到自己建的（和旧版迁移过来的）会话。
- 一个回答还没跑完就切走也没关系，结果回到原来的会话，并提示是哪个会话有了结果。

助手先看问题问的是什么，再决定去哪里找答案：

- **平台本身**（失败、卡住、进度、在跑什么、等谁验收、点数）：直接从平台记录回答，不调模型，不扣点；开着“深入分析”也一样，因为智能体看不到这些记录。失败会按原因归类（模型满载、没登录、超时、构建没过……），并给出“重试这 N 单”按钮，点了先确认，再从每单停下的那一步接着跑。
- **某张工单**（“这单怎么了”，或直接写 JB-5）：这单最近一步做到哪、为什么失败、在等谁。
- **追问**：“都重试”“那审批呢”接着上一条回答的对象，不用把话说全。
- **业务和代码**：走下面两种模式。查不到明显对得上的知识时直说，不再把最接近的业务流当成“最相关”；回答下面有“让智能体读代码深入查”，不用先切模式。

回答下面会给出下一步可问的话，点一下就发。

两种模式：

- **查项目知识**：直接在知识库和代码索引里找相关业务流、表和代码位置，不调模型，不扣点。问句里的“在哪里、怎么、是”这类词会先去掉，标题命中的页面排在前面。
- **分析与起草**：让本机智能体只读代码作答。回答分三段：结论与边界、依据（每条标【核实】或【推断】）、下一步；没证实的根因写“待确认”。

依据卡片默认显示 3 条，其余收在“其余 N 条依据”里。会改动东西的操作（分析、方案、改码）先出确认卡片，点确认才执行。助手可以起草验收说明，但不会替人点验收。

**起草工单**：从会话整理出标题、现象与复现、排查情况、依据，根因保持“待确认”，负责人和验收条件不知道就留空。核对后点“提交工单”才会创建，取消什么都不留；同一次提交重复点只建一张。已经关联工单的会话默认是“补充到该工单”（加一条评论），也可以选“另建工单”。

### 提示词标签页

工单页的“提示词”标签按场景把工单、关联的业务流、表、代码位置和知识页拼成一段提示词，可以粘贴到 Cursor、Claude Code、Codex 或任何对话里。场景有五个：修复缺陷、新增字段、信创适配、补测试、解释业务，每个场景有自己的步骤和约束。

- **复制提示词**：只复制，并在工单动态里记一笔。
- **写入 Cursor 规则**：写 `.cursor/rules/tmh-ticket.mdc`（`alwaysApply: true`）。
- **写入 CLAUDE.md**：在项目 `CLAUDE.md` 末尾写一段带 `<!-- tmh:ticket:start -->` 标记的临时段落，换单时替换，不碰文件里的其他内容。
- **从项目里清除**：删掉上面两处临时内容。

写入时还会写 `.tmh/current-ticket`，之后 IDE 里的 MCP 调用会记到这张工单上。复制和写入都计入 AI 参与率。

### 提效报告

数据全部从平台记录里算，不需要人填：

| 指标 | 怎么算 |
|---|---|
| 工单周期 | 工单创建到人工验收通过，取中位数，按类型分 |
| 首次定位耗时 | 工单创建到第一次“分析定位”或“修改方案”运行完成 |
| 验收退回率 | 有验收记录的工单里，至少被退回一次的比例；同时给出返工次数 |
| AI 参与率 | 经手的工单里，有智能体运行、助手对话、提示词使用或 IDE 里 MCP 调用的比例，并按这四种来源拆开 |
| 每单 AI 成本 | 点数账本里记到工单上的消耗，按工单平均；不归属工单的消耗单独列出 |
| 节省人天（估算） | （基线周期中位数 − 本期周期中位数）× 本期关闭工单数。周期是日历时间，不等于工时，所以标“估算” |

**基线**：在“外部系统”导入过去 3～6 个月的 Jira 或禅道工单。在原系统里已经关闭、之后没在平台上处理的工单就是基线，用原系统的创建和解决时间（Jira 的 `resolutiondate`，禅道的 `closedDate`/`resolvedDate`）。导入后又在平台上处理的，算本期，创建时间取原系统的。

**导出**：页面右上角选月份，“导出报告（Markdown）”下载 `AI提效报告-<代号>-<月份>.md`；“打开可打印版”打开 `/p/<代号>/efficiency?month=2026-10`，用浏览器打印成 PDF。报告里“实测”和“估算”分开标注。

**IDE 侧使用**：`tmh mcp` 每处理一次工具调用，就在项目的 `.tmh/usage.jsonl` 追加一行（时间、客户端名和版本、工具名、工单号、是否成功）。工单号从调用参数里认（如 `TOG-12`），认不出时用 `.tmh/current-ticket`。平台自己发起的运行带 `run` 字段，不重复计数。

### 点数

顶栏显示剩余点数，点开看流水。每次智能体运行结束按模式扣点：助手问答 3、分析 10、方案 10、改码 30、知识页 5，演示环境初始 20000 点。价格和初始额度可以写在 `<数据目录>/pricing.json` 里覆盖，例如 `{"prices": {"fix": 50}, "initial": 5000}`。

## 智能体怎么跑

| 任务 | 在哪里跑 | 权限 |
|---|---|---|
| 分析定位、修改方案 | 项目目录 | 只读：Claude Code 只开放读文件、搜索、`tmh` 和只读 git 命令；Codex 用 `--sandbox read-only` |
| 修改代码 | 平台数据目录下的独立 git 工作树（分支 `tmh/<工单号>-r<运行号>`） | 可改文件，不提交。按文件分工的智能体只能改自己负责的文件；诊断只读。改完跑构建测试，见“修改代码怎么做”。结束后平台记录完整 diff。自动流转里通过守门检查就自动提交到该分支；否则由人“采纳”（提交到该分支，等你合并）或“放弃”（删除工作树和分支） |
| 撰写知识页 | 项目目录 | 只改 `.tmh/knowledge/` 下的页面，写完运行 `tmh kb done` 校验 |

- 修改代码需要项目是 git 仓库。不是的话先在项目目录执行 `git init && git add -A && git commit -m 基线`。
- 平台调用本机已安装的 `claude` 和 `codex` 命令，沿用它们自己的登录。接国产模型用 `tmh agent-config` 生成配置，在启动平台的终端里设置好环境变量。平台不保存任何密钥。
- 每次运行交给智能体的完整提示词都能在运行详情里点“提示词”查看。
- 自研或其他智能体：在 `~/.tmh/platform/agents.json` 里登记命令模板，`{prompt_file}`、`{prompt}`、`{workdir}`、`{mode}`、`{model}` 会被替换。

### 选模型

工单的“执行过程”、维护助手的“分析与起草”、知识页“让智能体撰写”和“全项目分析”，在智能体旁边都有一个模型下拉框，每次启动时选：

| 选项 | 效果 |
|---|---|
| 自动（默认） | 按任务类型选：Claude Code 做修改方案和修改代码用 Opus，分析定位、撰写知识页、助手问答用 Sonnet |
| Opus、Sonnet、Haiku（Codex 是 GPT-5 Codex、GPT-5） | 这次固定用这个模型，Claude Code 加 `--model`，Codex 加 `-m`，会替换 `agents.json` 里写死的同名参数 |
| 沿用本机设置 | 不传模型参数，用智能体自己的配置 |

浏览器会记住每个智能体上次选的模型。用了哪个模型记在运行记录里，在运行详情、工单动态和“智能体运行”里都能看到；Claude Code 启动时报告的实际模型也会出现在运行输出的第一行。可选模型和自动规则可以在 `agents.json` 里改：

```json
{"claude": {"timeout": 1800, "defaults": {"analyze": "opus"}},
 "codex": {"models": [["gpt-5-codex", "GPT-5 Codex"], ["o3", "o3"]]},
 "my-agent": {"title": "自研智能体", "cmd": ["my-agent", "--model", "{model}", "--prompt-file", "{prompt_file}"],
              "models": [["qwen3-coder", "通义 Qwen3 Coder"]], "defaults": {"fix": "qwen3-coder"}}}
```

接口上，启动运行的请求（`/api/tickets/<工单号>/runs`、`/api/projects/<代号>/runs`、`/survey`、会话提问）都可以带 `"model"`：不带或 `"auto"` 按自动规则，`""` 沿用本机设置。

## 全项目分析

知识库页顶部的“全项目分析”让本机的 Codex 或 Claude Code 写完整个知识库，不用在终端里操作：

1. 先构建（或增量刷新）知识图谱，等同 `tmh kb build`。
2. 按 `tmh kb next` 的队列逐页撰写：先业务流，再表，再业务域，最后系统总览，上层页面引用下层页面的摘要。可以并行 1 到 4 个智能体，每页是一次独立的“撰写知识页”运行，过程和结果都在“智能体运行”里。
3. 每页必须通过 `tmh kb done` 校验（结论带 `文件:行号` 证据）才算写成，状态是“待确认”，由人确认。
4. 结束后刷新业务全景报告。

**范围有两种，默认是“业务地图”。**

- **业务地图**：只写业务域和系统总览。业务域直接用工具解析出的业务流事实（入口、处理方法、读写的表、代码位置）来写，不等业务流页写完，最后写系统总览。页数通常只有全写的一小部分，用来先看清整个系统。
- **全部页面**：业务流、表、业务域、总览全部写。大项目页数上千，token 消耗很大，适合重点项目分批跑。

业务流和表的“事实部分”是工具自动解析的，不花 token，没写“业务理解”的页面也能被工单分析用上。

**按需补写**：工单页“智能体”卡片里勾选“分析定位后，顺手补写涉及的业务流知识页”（默认勾选），分析结束后平台会把结论里点到的、以及工单已关联的业务流中还没写的页面补写上，每次最多 2 页，结果记在工单动态里。这样知识库跟着真实工单一点点长全，钱花在有人用的业务上。接口参数：`POST /api/tickets/<工单号>/runs` 带 `"kb_after": 2`。

可以设“本次最多写几页”。第一次建议先试跑 5 页看质量，再继续。中途点“停止”，正在写的页面写完就停；下次点“继续全项目分析”从剩下的页面接着写。第一批页面就失败时（多半是智能体没装好或没登录），平台会自动停下。

接口：`GET /api/projects/<代号>/survey` 查看进度，`POST /api/projects/<代号>/survey` 开始（`{"scope": "top", "agent": "codex", "parallel": 2, "limit": 5}`，`scope` 为 `top` 或 `all`），`POST /api/projects/<代号>/survey/stop` 停止。

## 群机器人和开放问答接口

业务方在钉钉、飞书、企业微信群里直接问，机器人按知识库原文做需求预判并在群里答复：结论、把握、依据页面；需要人判断的记进待答问题，回复“已转人工 #n”。配置里列出的答复人可以在群里发“答复 #n 原话”写回知识库，发“改判 预判编号 理由”标记预判不对。

在项目的 `.tmh/config.json` 里加 `"bots"`（只写环境变量名，字段说明见 `tmh/bots.py` 开头），回调地址填：

| 平台 | 回调地址 | 校验方式 |
|---|---|---|
| 钉钉企业内部机器人 | `/bot/dingtalk/<代号>` | 请求头 timestamp + sign（AppSecret 加签），一小时内有效；答复发到消息里的 sessionWebhook（只认 dingtalk.com） |
| 飞书自建应用（事件订阅 im.message.receive_v1） | `/bot/feishu/<代号>` | Encrypt Key 解密和签名，或 Verification Token；用应用身份回复原消息 |
| 企业微信自建应用（接收消息） | `/bot/wecom/<代号>` | msg_signature + EncodingAESKey 解密（AES-CBC，纯 Python 实现）；用应用消息回发给提问人 |
| 开放接口 | `POST /bot/api/<代号>`，`{"text", "sender"}` | 请求头 `Authorization: Bearer <密钥>`；同步返回结论 JSON |

这些地址不走平台的访问令牌，靠各平台自己的签名，所以平台要能被这些平台访问到（反向代理或内网穿透）。私有化部署的飞书、企业微信可在配置里用 `base_url` 改成内网地址。“知识库 → 待确认”页能看到各机器人是否就绪（`GET /api/projects/<代号>/bots`）。

## 自动流转

工单不管从哪里来（新建、导入、助手起草、群里转来的），都走同一条线，不用人点按钮，一直做到“改动已提交到这张工单自己的分支，等人验收”：

1. **自动受理**：按标题和描述在知识库里找涉及的业务流，最多关联 3 条，记一条“自动受理”动态。
2. **分析定位**：交给本机智能体（默认第一个可用的，可在 `<数据目录>/autoflow.json` 指定），然后转“处理中”。没找到代码证据、分析失败或本机没有智能体，就停在“处理中”，动态里写明需要人补什么。
3. **修改方案**：找到代码证据就接着起草方案。方案最后附一份文件清单：要改的文件，以及必须跟着改的调用方、配置和测试，每个文件一句目标。
4. **修改代码**：在独立 git 工作树里改（分支 `tmh/<工单号>-r<运行号>`），主干和你的工作目录都不动。怎么改见下面“修改代码怎么做”。
5. **自动提交**：改动通过守门检查，就提交到该分支，工单转“待验证”，动态里写明分支和提交号。合并到主干、按业务验收仍由人来做。

守门检查不通过时不提交，改动留在“等你审阅”，动态里写明原因：

- 改动行数超过 `max_lines`（默认 400；可按项目分开设，如 `{"JB": 400, "RW": 20000}`）；
- 改了已有的测试或受保护文件（项目 `.tmh/config.json` 的 `protected`，以及常见测试目录和文件名）；新增测试可以；
- 删除了文件；
- 改了几轮后构建或测试仍没通过，或诊断认为还没解决工单。

**人随时可以介入**：工单详情标题下的“自动处理中 · 接管”点一下就暂停，正在跑的那一步跑完后不再往下走，之后的分析、方案、改代码、采纳都由人来；点“交回自动”从停下的那一步接着走（已有改动就重新过守门检查再提交）。人手动发起的运行也不会再自动接下一步。

```json
{"on": true, "agent": "codex", "plan": true, "fix": true, "commit": true, "max_lines": 400, "assignee": "",
 "resume": true, "max_agents": 4, "split_from": 5}
```

**一张单一个会话**（`resume`，默认开）：方案接着分析的智能体会话做，改代码接着方案的会话做，诊断后的下一轮接着改代码的会话做。接着做的那一步只收到新任务和之后补充的信息，不再重发工单和知识库，也不用把读过的代码再读一遍。会话接不上（智能体那边已经没有了）就自动新开一个会话，发完整提示词。

**同时运行的智能体**（`max_agents`，默认 4，0 不限）：超出的运行排队，工单的分析、方案、改代码排在补写知识页前面；会话问答不排队。

**每一步用时**：每次调用智能体，运行日志末尾都有一行“用时 N 秒：启动、模型、命令、钩子、token”，明细在 `<数据目录>/runs/<运行号>/timing*.json`。启动包括连接，模型是等回复和网络的时间。

### 修改代码怎么做

参考 HERMES（arXiv 2610.07832）的做法，每次“修改代码”（自动的和人点的都一样）分四步，日志里逐步可见：

1. **按文件分工**：方案列出的文件不到 `split_from` 个（默认 5）时，由一个智能体接着方案的会话整体改，一两个文件的改动拆开只会多花时间。文件多时，每个文件交给一个只负责它的智能体。它只能改自己的文件，别的文件需要配合时发消息（接口变了、调用方要跟着改、测试要补）；收到消息的文件再改一次，清单外的文件被点名就加进来（最多 `max_files` 个，默认 16）。智能体改了不归它的文件，平台会撤回。方案里没有文件清单时，由一个智能体整体改。
2. **构建测试**：在工作树里跑构建和测试。命令按这个顺序找：`autoflow.json` 的 `check`，项目 `.tmh/config.json` 的 `commands`，再自动识别（`mvnw`、`pom.xml`、`gradlew`、`build.gradle`、`*.sln`，根目录没有就看一层子目录，比如 `backend/`）。先在没改过的代码上跑一次，原代码在这台机器上就跑不通的话，这条命令说明不了问题，跳过并写明原因。
平台不跑构建测试时（`check` 设成 `none`，或原代码就跑不通），会明确告诉智能体不要自己去编译、启动服务或改构建配置。

3. **诊断**：用最强的模型读改动和构建测试结果，判断工单是否真的解决。构建或测试失败一律算没解决，模型说了不算。没解决就指出证据、原因、该改哪些文件。
4. **再改**：只把诊断点名的文件交回去重改，最多再改 `rounds` 轮（默认 3 轮，论文里 3 轮之后几乎不再提升）。

工单详情的下一步提示里写明结果，比如“3 个文件分工改，构建测试通过，诊断认为已解决，共 2 轮”。完整过程在运行结果和 `<数据目录>/runs/<运行号>/verify.json`。

模型分工：Claude Code 默认方案和诊断用 Opus，按文件改用 Sonnet，整体改用 Opus；人手动选了模型时每一步都用它。可在 `agents.json` 的 `defaults` 里改（`edit`、`diagnose`）。

```json
{"check": "cd backend && mvn -q -B -o test", "rounds": 3, "check_timeout": 1200, "max_files": 16}
```

`check` 不填就自动识别，填 `"none"` 不跑，也可以按项目填：`{"OA": "mvn -q test"}`。

`on: false` 整条线关掉；`fix: false` 只自动做到修改方案；`commit: false` 改完代码留给人审阅、不自动提交；`assignee` 填了就自动指派。导入的已关闭历史工单不会触发。

`refix`（默认 2）：自动提交的改动验收不通过时，带着退回原因在被退回的分支上自动重改的次数，超过就转人工；填 0 不重改。

## 重构升级

重构、升级这种大改动，拆开后每一块都是普通的改动工单，所以复用同一条线：

- **拆分**：按知识库里的业务域，一个业务域一张工单。顺序按牵连从少到多排：和别的业务域共用的表越少、业务流越少、调用链断开（动态表名、反射）越少的越靠前，排在最前的当试点。牵连分低、中、高三档，按顺序三等分。
- **工单内容**：改造目标、这类改造的要求、不能变的东西、只改这个业务域、涉及的入口文件、和别的业务域共用的表（读写方式不能变）、验收条件（构建测试通过、业务流行为不变）。类型是“变更”，自动关联这个业务域的业务流。
- **放出**：建计划不开单。点“放出第一批”按每批张数开单，开出的单直接进自动处理（分析、方案、按文件改、构建测试、诊断、提交到独立分支，停在等验收）。
- **按验收结果推进**：和修问题是同一套循环，只是高一层。单张单验收不通过会自动重改（`refix`），计划则在验收通过时往前走：开着“自动推进”（默认开）时，已放出的单全部验收通过，就自动放出下一批。某一块自动重改用完后仍不通过（或没有可重改的自动改动），计划暂停自动推进，页面上标出原因，人处理好后点“恢复”。手动“放出下一批”也会解除暂停。
- **经验带给后面的单**：前面几块验收时写的话（通过时的说明、不通过的原因）写进后面放出的工单正文，标题“前面几部分验收时说的”，最多 10 条。
- **计划日志**：放出、通过、退回、暂停、恢复都记一行，计划卡片展开后看最近 6 条。
- **依赖清单**：从 `pom.xml`（含父 POM 和 properties 里的版本）、`package.json`、`.csproj` / `packages.config`、`requirements*.txt` 读出声明的依赖和版本，写升级目标时对照。
- 计划存在 `<数据目录>/reforms/<代号>.json`。删除计划不删已经开出的工单。

## 闭环改进

### 结果回流
- **验收不通过**：记一条教训（退回原因、被退回的改动碰了哪些文件、关联的业务流）。这张单之后的提示词里会有“验收没通过”一节，原话照搬。改动是自动提交的，就按 `refix` 自动重改：新分支从被退回的分支接着改，改完照常构建测试、诊断、提交，再停在等验收。
- **验收通过，但自动提交之后有人又在分支上提交过**：也记一条教训，内容是人补的提交说明、文件和一段差异。
- 之后的工单起草方案、改代码时，提示词带上最相近的 3 条教训（同一业务流、提到同一文件、描述相近），标题“以往的教训”。教训存在 `<数据目录>/lessons.jsonl`，每行一条，可以手工删改。

### 评测集
- 自动改动验收通过的工单自动成为用例：起点是第一次自动提交之前的那个提交，答案是从起点到分支最新提交改过的文件（人后来补的也算）。也可以在“闭环改进”页手动加（标题、描述、该改的文件，起点可空）。存在 `<数据目录>/evals/<代号>.json`。
- **从历史工单生成**（“闭环改进”页 → 用例 → 从历史工单生成用例）：先导入已关闭的老工单：点“先导入提交里提到的已关闭工单”，按提交信息里出现的单号从已接入的工单系统（禅道、Jira、GitHub、GitLab）逐个拉取，“fixes #12”“close TOG-3”这类写在修复词后面的先查；GitHub 上提交写的多是合并请求号（`Merge pull request #20`、`(#20)`），已合并的合并请求在标题或描述里用 Fixes/Closes 关掉的 issue 也导入，并记下是哪个合并请求修的。还开着的不导；查过没结果的单号记住不再查，GitHub 调用次数到上限时停下，下次点接着导（公开仓库不带 token 每小时只有 60 次，建议配 `GITHUB_TOKEN`）。然后按关闭时间范围预览。项目仓库当前分支上提交信息写了工单号的提交算修复提交（`TOG-12`、`bug#123`、`Bug 123`、`#123`；`#123` 只在只有一张单是这个编号时才认），找不到的单直接跳过，不按时间猜。合并提交也算：答案是它相对第一个父提交的整个改动。起点是最早一个修复提交的（第一个）父提交；答案是这些提交改过的文件，去掉锁文件、构建产物和只改空白的；工单文本只用当时的标题和描述，不带后来的评论。改了 15 个以上文件、或只改配置和 SQL 的单会标出来，默认不入库。这类用例标“历史工单”，回放结果按来源分开算。
- “回放全部用例”：每个用例在起点提交上建一个临时工作树，让智能体照真实工单起草修改方案，把方案里列的文件和 `文件:行号` 跟答案对：**找全率** = 该改的文件列出了几成，**准确率** = 列出的文件里有几成真该改。换模型、改提示词、补知识库之后跑一遍，看分数是升是降。结果在 `<数据目录>/evals/results.jsonl`，回放的每次运行在“智能体运行”里能看到。
- 知识库用的是现在的，不是当时的，分数会略偏乐观。

### 告警自动开单
在 `<数据目录>/alerts.json` 里按项目开启，只写环境变量名：

```json
{"TOG": {"key_env": "TMH_ALERT_KEY_TOG", "per_hour": 20}, "*": {"key_env": "TMH_ALERT_KEY"}}
```

监控往 `POST /hook/alert/<代号>` 发，带 `Authorization: Bearer <密钥>`（发不了请求头的用 `?key=`）。这个地址不用平台令牌，局域网里的监控也能直接发（平台要用 `--host 0.0.0.0` 启动并设好 `TMH_TOKEN`）。认得：Alertmanager（Prometheus、Grafana）、SkyWalking 告警列表、带 `title`/`summary`/`message` 和 `description`/`text`/`stack` 的 JSON、纯文本（第一行当标题）。日志平台（ELK Watcher、Loki Ruler 经 Alertmanager、阿里云 SLS 告警等）配成往这里发即可。

- 同一告警（Alertmanager 的 fingerprint；没有就按服务 + 去掉数字后的标题）已经有未关闭的单，就只累计次数，每 10 分钟最多留一条评论；恢复通知在单上记一笔。
- 堆栈（Java、Python、.NET、Node）里属于本项目的帧对到仓库文件，写进“## 堆栈里的项目代码”，框架代码不算；对到了就是“缺陷”，否则是“运维”。
- 级别换成优先级：critical / fatal / P0 → 紧急，error / P1 → 高，warning / P2 → 普通，info → 低。
- 开单后直接进自动处理（自动分析、方案、改代码、提交，停在等验收）。每个项目每小时最多新开 `per_hour` 张，多出来的只计数不开单。
- “闭环改进”页可以直接贴一段告警或报错日志开单，处理方式一样。

## 知识库检索

工单、助手、智能体提示词都用同一个检索（`tmh context`）。针对几十万行的项目做了三件事：

- **业务词归一**：去掉“一直转圈”“提交不了”这类症状词，按已知业务词切分（不再出现“销单”“单提”这种跨词片段），并补上代码里的常见叫法（报销→expense/reimburse，提交→submit/save/commit，XX单→单据/bill）。
- **领域优先**：先看排在前面的结果集中在哪几个业务域，再提升这些域里的业务流、表和代码，压低其他域里字面相近的结果；超长页面按长度折算，不再因为“什么都提一句”排第一。
- **索引缓存**：索引按知识库版本缓存在内存和 `.tmh/cache/search.idx`，知识库或图谱变化后自动重建。together-project（约 4.9 万条）首次 4.5 秒，之后每次 0.03 秒。

## AI 助手：一句话操作页面

右侧的 AI 助手既能提问，也能替你操作页面。任何页面按 Ctrl+K（Mac 上 ⌘K）呼出，同一个输入框里直接说：

- 跳转：“打开知识库”“去提效报告”“OA-12”“打开知识库里的请假审批”
- 代填并提交：“给这单写评论：需要前方实施人员去现场取日志”“验收不通过，原因是导出少一列”“新建工单：审批后单据未生效。用户反馈……”
- 改字段：“把这单改成待验证”“优先级改成高”“指派给张三”，或当前页面上任何字段：“验收说明写：……”
- 会话和项目：“新建会话 审批问题”“切换到审批的会话”“切换到项目 OA”

助手先把这句话拆成步骤显示在会话里：跳转、填写这类可撤回的步骤直接做，内容填在页面上、高亮出来；
每次操作在对话里是一张卡：要提交、保存或改工单字段时停在“待你确认”，确认前可以先在页面里改；改状态、类型、优先级也先确认，执行后卡片显示“已执行”并带“撤销”，一键改回原值。弹出的表单不会挡住助手。
每条指令和执行结果都记在当前会话里，“会话与导航”里能看到所有会话、常用页面和最近访问。

常见说法由规则直接识别，不需要模型，不扣点。配置了转发模型（`router`，见需求预判）时，规则认不出的模糊说法
（“让前方去现场拿日志，记到这单上”）交给模型理解，模型只能使用当前页面上真实存在的字段和按钮，结果再经过校验；
认不出或像在提问的话，按普通提问回答。

## 测试机

改完代码后，平台可以把改动发到另一台机器（测试机）上编译和测试，结果交回给智能体再改一轮。智能体本身不碰测试机。

- 在“设置 → 测试机”里填 `用户名@主机` 和端口。只用 SSH 密钥登录（BatchMode），平台不保存密码；运行平台的这台机器要能用 `ssh -p 端口 用户名@主机` 免密登录。
- “体检”列出测试机上有哪些工具（Git、JDK、Maven、Node、pnpm）。缺的可以点“下载安装缺的工具”，在测试机上下载免安装版，解压到工作目录的 `tools/` 下（Windows，不需要管理员权限）。
- 代码第一次让测试机自己从 origin 拉（公开仓库），拉不到就由平台打包发过去；之后只发缺的提交。每次构建都在工单固定的那个提交上应用改动，只保留 `node_modules`、`target` 这类缓存。
- 默认只编译改到的部分：改到的 Maven 模块（`mvn compile -pl … -am`），以及改到的前端的类型检查。项目 `.tmh/config.json` 的 `commands` 或 autoflow 的 `check` 可以换成自己的命令。
- 每张单的改动还会和方案对照：改了方案没列的文件，会在结果里标“超出方案”，自动处理也不会提交，留给人看。
