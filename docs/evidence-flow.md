# 证据流：证据包、甲方签收页、基线闸门和账本

工单闭环从“任务流”改成“证据流”：每次状态变化都留下一个不可改、可追溯、归甲方所有的对象。这是《厚重化迭代方案》第一批的前三项（第 1、2、4 项），目标是能演示“AI 备齐证据、人签字、账本自动出”。

## 1. 证据包（`tmh/evidence.py`、`tmh/platform/signoff.py`）

- 工单转到“待验证”时自动打包：方案里的验收标准（AC）和验法、方案列的文件（变更契约）、改动文件和行数、构建测试结果、是否超出方案、改动是否落在本单关联的业务流上（按文件）、谁采纳了改动。
- 之后的补截图、乙方复核、发签收链接、甲方签收或退回、平台里的“验收通过/不通过”都追加在后面。每条记录带前一条的哈希；改、删、插任何一条，`check` 都会指出第几条对不上，证据包也不再接受追加。
- 缺项（任何一项缺都标“证据不齐”）：验收标准、代码改动、构建或测试结果、改动没超出方案、改动落在本单业务流上、乙方复核人。超出方案或不在业务流上的改动，复核人写明理由后可以认可。
- 存放：`<数据目录>/evidence/<工单号>.jsonl`，截图在 `evidence/files/<sha256>.png`。整包单页：`/e/<工单号>`（要登录）。
- 命令行任务契约同样打包：进入“待人工验收”或“自动证据齐全”时打包，`confirm` 记签收（带所签证据包的哈希），`close` 记关单，退回记原因；`tmh accept evidence T001` 看哈希链。“自动证据齐全”要求证据包里有本地验证、入口路径检查和部署构建号。

## 2. 甲方零代码签收页

- 工单在“待验证”时，乙方在工单页“证据包”卡片里点“发签收链接”，填签收人姓名和角色。证据不齐时要写明为什么现在就请甲方签。
- 链接 `/sign/<一次性口令>`，默认 7 天有效，只能用一次，新链接会作废旧的；口令只出现在链接里，平台只存它的哈希。
- 页面只有：问题描述、改的是哪项业务（业务流名称和业务域）、验收标准逐条（怎么验、结果、截图）、乙方准备情况、证据包封印。没有代码、文件名、分支。
- 签收人要输入自己的姓名，逐条点“通过”才能签收；有一条不通过就退回，必须写原因。签收或退回写进证据包，同时走和平台“验收”按钮一样的路径：签收关单，退回转回处理中（自动处理开着时带着原因重改）。

## 3. 基线闸门和账本（`tmh/platform/books.py`、`metrics.py`）

- 基线只封存一次：在提效报告页选窗口（按原系统解决时间），把窗口内导入的已关闭历史工单的口径、样本清单、统计写进 `<数据目录>/baselines/<项目>.json` 并算哈希，文件设为只读。再封存会被拒绝；文件被改过则按“没有基线”处理。
- 没有封存基线时：报告只出本期实测，对比列写“未封存”。
- 账本每单一行：周期、首次定位、返工次数、AI 运行次数、点数、标价折人民币、实付、人工动作次数、证据包状态和签收人。报告里新增“账本（每单）”和“验收证据抽样”（已签收的里固定种子随机抽 5 张，带证据包哈希）。

## 4. 外部 PR（`tmh/platform/upstream.py`、`tmh/integrations/github.py`）

给开源老项目提的 PR 也是一张工单：`links.upstream` 记仓库、issue 和 PR 号，所有动静写进同一个证据包。

- 起草：标题、描述、分支、目标分支，存一份草稿并算哈希。
- 批准：提交 PR 是用 Li 的账号对外发布，必须由人批准，批准记下草稿哈希；草稿改过就要重新批准。
- 提交：只提交被批准的那份草稿；不带 `confirm` 只演练，不发出去；真提交要本机设置 `GITHUB_TOKEN`。
- 跟踪：“从 GitHub 同步”读 PR 状态、CI、每轮评审原文和提交记录；状态变化、新的评审、CI 结果都追加进证据包。维护者合并就关单，记“上游维护者”为验收人；关闭未合并就退回处理中，并要求补记原因。
- 指标（报告里的“外部 PR”一节，替代节省人天）：合并率、合并前评审轮次、提交到合并时长、维护者合并前又加提交的个数、关闭原因分布、每个合并 PR 的 AI 点数。全部能在 GitHub 上复查。

## 5. 改得对不对：验证门（`tmh/platform/gates.py`）

"构建过了"不等于"改对了"。每次改动按成本从低到高过 9 道门，每道给出 通过 / 没过 / 未知，连同依据写进证据包：

| 门 | 看什么 |
|---|---|
| 有实际改动 | 不能只改空白和换行 |
| 改后的文件能解析 | Python、JSON、XML 在平台上直接解析；其他语言看构建 |
| 没有削弱测试 | 删测试文件、删断言、加 `@Ignore`/`@Disabled`/`it.skip`/`pytest.mark.skip`、加 `\|\| true`、`-DskipTests`、`continue-on-error`、调低覆盖率门槛，命中就是没过 |
| 没超出方案 | 只改了方案列出的文件 |
| 落在本单的业务流上 | 原来的入口路径检查 |
| 原代码能构建 | 基线体检：先在没改的代码上跑一遍，原本就坏的不算到这次改动头上，结论记为未知 |
| 构建通过、测试通过 | 构建测试的退出码 |
| 对照验收标准改对了【推断】 | 诊断智能体逐条对照 AC：等价、只对了一部分、方向不同、改错了。只是推断 |

- 证据包里"验证门全部通过"取代原来的"构建或测试结果、没超出方案、在业务流上"三项；未知也算没齐。旧证据包仍按原来的六项判断。
- 人可以在"复核"里逐道写理由放行，理由和名字进证据包；构建或测试没过不能放行，只能改代码。
- 提交上游 PR：批准和提交前都检查验证门。有没过的就拒绝；有未知的，批准人要写明为什么仍然提交。
- 甲方签收页只显示"9 道，通过几道"，不显示依据（依据里有文件名）。

## 6. 理清需求：从一句话到可验收的工单（`tmh/platform/intake.py`）

新建工单里点“说不清楚？让平台帮你理清”，或调接口 `POST /api/projects/<项目>/intake {"text": "…"}`：

1. 一句话里说了几件事就拆开（“另外”“还有”“1. 2.”），每件以后各建一张单。
2. 分成缺陷、新需求、咨询、数据问题。配了转发模型就让它选（只选，不生成），否则按关键词；人可以改。咨询直接用知识库答复，不建单。
3. 复述理解并挂到业务地图上：“我理解的是……涉及业务流「审批通过」和表 OA_LEAVE”，让对方选是哪一块。
4. 只问缺的，每轮最多 3 个，能选的给选项；原话里已经说了的（什么时候开始、谁遇到、什么操作时、期望什么）不再问。
5. 要一个具体例子（谁、做了什么、什么数据、结果应该是什么），写进验收标准的“怎么验”。
6. 验收标准用 EARS 句式“当……时，系统应当……”，另加一条“必须保持”；没说清的写“待确认”，不猜。
7. 对方确认才建单。确认人、时间和验收标准作为证据包的第一条记录（需求确认）。

接口：`GET /api/intake/<id>`，`POST /api/intake/<id>` 的 `action` 为 `answer`（`answers: {"0": {"trigger": "…"}}`）、`confirm`、`drop`。

## 7. 框选定位：在页面上圈出问题，找到代码（`tmh/platform/pinpoint.py`）

“外部系统”页的“框选定位”卡片生成一个书签（每个项目一个，只能往平台加框选记录；重新生成后旧的失效，平台只存它的哈希）。甲方在自己系统的页面上点书签，拖一个框，说一句话。框里的东西作为数据发过来，不是截图：页面地址、看得见的文字、元素的 id 和字段名、源码标记、页面发出的接口请求。平台分三层找代码：

1. 源码标记。前端用 code-inspector-plugin 或 Vue inspector 构建的，元素上带 `文件:行`，精确到行。只有新前端有。
2. 知识库匹配，给 JSP、FreeMarker、OFBiz 表单这类老模板用。框里的文字先在模板里找，再经标签文件（.properties、`*UiLabels.xml`、语言包 JSON）反查到标签键，再找用这个键的模板，例如“培训日期”→ HumanResTrainingDate → EmployeeTrainingForms.xml。字段名、id、页面地址也算分；越少见的文字分越高。结果是推断，列出每个候选文件靠什么匹配上的。
3. 接口反查，给“数据不对”用。页面发出的请求对到调用图里的入口，再到业务流和它读写的表。

都没找到就写明“转人工看”。每条框选记录可以点“理清需求并建单”，进入上一节的需求对话，定位结果写进工单的“位置”一节。

接口：`POST /api/projects/<项目>/capture-token`（生成书签）、`GET|POST /api/projects/<项目>/pins`、`GET /api/pins/<id>`、`POST /api/pins/<id>/intake`；书签发到 `POST /capture/<书签令牌>`，不需要登录。

## 8. 经验库：验收结果变成经验卡，记下用了以后有没有帮上忙（`tmh/platform/learn.py`）

原来的"教训"只是一句退回原因。现在每条是一张经验卡：现象、根因、改法、验法、别这样改，加上涉及的文件、来自哪张工单、当时证据包的哈希和签收人。设计依据和出处见项目共享文件夹 `rsi/01-记忆与经验复用.md`。

- **只从人的结论学，不信智能体自评。** 验收没通过、自动提交后有人又改过，直接生成"在用"的卡；自动改动原样通过、而且是签收（或上游合并）在验证门没失败的证据包上，生成一张"待确认"的卡，人确认后才用。签在没过的验证门上的，是人的判断，不当成做法来学。
- **状态**：待确认 → 在用 → 暂停（跟着失败的次数多于通过、且失败满 2 次，自动暂停，等人看）或停用（人停用，必须写原因）。暂停和停用的卡可以恢复。
- **只放"在用"的卡进提示词**，按业务流、文件、文字相近度打分，每次最多 3 条，分数不够宁可不放。卡上的文件如果当时在主代码里、现在全都没了，这张卡不再放。提示词里写明"只作参考，先核实；用了写编号"。
- **记账**：哪张工单的提示词带了哪些卡（到下一次验收前只记一次），这张工单验收通过还是没通过，智能体的结论里有没有引用卡的编号。这些都追加在 `<数据目录>/lesson_log.jsonl`，卡本身那一行写下后不再改；人改字段、改状态也是追加一行，谁、什么时候、为什么都留着。
- **闭环改进页的"经验库"**：每张卡显示状态、被用过几次、之后通过和没通过各几次、被引用几次、来自哪个证据包；可以确认入库、修改字段、停用、恢复。顶部统计在用、待确认、暂停、停用的张数和"用过的经验之后的验收通过率"。

接口：`POST /api/projects/<项目>/lessons/<编号>`，`action` 为 `confirm`、`restore`、`retire`（要带 `why`），或带 `fields: {"symptom"|"cause"|"fix"|"verify"|"anti": "…"}` 修改。`GET /api/projects/<项目>/learn` 多了 `lesson_summary`。

还没做（下一轮候选）：跨项目共享（脱敏后只留技术栈、错误类和步骤）、按报错堆栈指纹检索、多张卡互相矛盾时不放、注入与不注入的对照实验。
