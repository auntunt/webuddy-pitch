# 验证与 Review

运行详情的“验证与 Review”展示三类结果：实际测试、AI 代码审查、人工复核与验收。工单证据包继续保存逐项实测证据；整体测试通过不能替代逐项业务验证。

## 自动和手动

- 修改代码的流程自动执行现有构建/测试，并对完成的改动进行只读 AI Review。没有执行环境时不反复猜测修复，但仍审查代码；缺少测试如实显示。
- “重新运行测试”只重跑检查；“重新 AI Review”只审查当前改动；“测试并 Review”依次执行两者。人工复核入口返回同一工单的证据复核位置，不自动签字。
- 项目的自动、观察、手动模式仍由原设置管理。本功能不改变项目模式，不自动打开验收或发布权限。固定候选的人工决定和个人隔离执行规则保持。

## API

`POST /api/runs/<rid>/recheck`，JSON `{"kind":"tests"|"review"|"all"}`。省略 kind 保持原 tests 行为。默认异步，返回运行号和操作号；`wait:true` 可等待结果。

`GET /api/runs/<rid>/recheck` 查询过程及当前验证。`GET /api/runs/<rid>` 同时返回 `verification.diagnosis.review` 的审查身份、版本与覆盖记录，以及绑定本次运行的 `human_review`。

人工入口保持 `POST /api/tickets/<key>/evidence`、`kind=review` 和 `POST /api/tickets/<key>/accept`，继续由服务器校验真人身份、角色、证据和版本。以上接口沿用原登录、租户、项目授权与执行限制。

## 版本与覆盖

完整 diff 按文件分批，大文件继续拆批，不截断内容。记录每批字符数和摘要、完整差异摘要、Git 基准、审查执行器、配置模型及各批结论。未完成、无有效结论、调用失败和二进制未验证范围不能标为完整通过。执行器是否不同明确显示，同一执行器的独立步骤不宣称交叉审查。

单独 Review 只有在代码、基准和旧验证均有效时保留原测试结果；否则显示待重新测试。审查期间代码变化不能发布通过结果。历史输出和验证保留；新操作共用原有持久锁、超时、进程回收及恢复记录，禁止并发重复复检。

AI Review 是代码推断；脚本退出成功是该脚本的执行事实；人工签收是独立业务决定。三者分别记录。

## 人工复核效果记录

运行详情的“Review 效果记录”允许有项目写权限的真人记录实际复核分钟数、每项 AI 发现的有效/误报/待核实判断、判断依据，以及人工另行发现的问题。记录绑定当时的完整审查摘要；重新审查后旧记录保留为历史，不能混入新审查的统计。保存记录不改变测试结果、采纳、验收或工单状态。

`POST /api/runs/<rid>/review-feedback` 使用运行详情返回的 `review_feedback.snapshot.binding`，并提交 `request_id`、整数 `minutes`、`findings`（原问题的 `id`、`verdict`、`reason`）、`missed` 字符串数组与 `note`。同一人同一请求号重复提交相同内容只保存一次；改变内容须使用新请求号。智能体不能代填。只读成员可看已有记录，不能保存。

效率页按同次审查、每位复核人的最后一条记录汇总。问题数量是人工判断次数，多人对同一问题的判断不等于多个独立缺陷。没有记录显示“未记录”，待核实不算有效发现；没有同范围的人工对照，不显示节省时间或效率提升百分比。


## 2026-11-06 验证流程修复

- 旧式构建命令和项目测试统一记录检查契约摘要，覆盖命令、项目测试配置、测试机配置、超时及实际验收标准。配置变化即使业务代码不变，也会使新格式旧证据失效；单独 Review 只有代码、基准和检查契约一致才复用测试，并记录复用原因。历史记录缺少契约时，不能通过 Review-only 重新取得有效测试状态。
- 项目测试先在独立的原始版本工作树运行基线；结果与候选报告分别保存。原始版本失败仍继续测试候选，不将原始问题当成新问题，也不虚构基线通过。首次运行原始版本可能需要重新安装依赖；依赖不足会保留实际受阻结果。
- 自动返修保存逐轮版本、差异摘要、命令、审查和影响文件。规划与审查明确声明新增场景、受影响旧功能、不变约束和范围缺口；没有声明或用例关联时不能宣称完整覆盖。声明属于审查判断，不代替用例实际执行。
- 本机旧式检查逐命令核对代码，项目测试逐阶段核对代码，发现版本变化后停止后续普通阶段并使整体结果无效；清理阶段继续执行。自动验证还比较整轮 HEAD、差异和契约，手动复检保留原有封存和操作锁。这里是版本检查与失效机制，不是操作系统级只读文件系统；不能防止拥有相同宿主权限的程序在一次检查内部修改后又恢复源码。
- 阶段另记 `execution_status`、`failure_kind`，区分未执行、环境/报告受阻、命令失败。汇总仍沿用原 pass/fail 兼容接口，必需阶段受阻不能通过。自动返修遇到已识别的验证受阻会停止修代码，保留证据待补齐条件。
- 验证出口区分问题处理、验证受阻和待人工复核；不会自动进入业务签收或关单。既有签收规则和人工补充依据路径保持，待人工复核不等于所有业务验收前置条件已经满足。原修复轮次和时间预算继续生效。

本次没有自动推导全部跨系统影响，也没有把通用回归配置转换为完整业务验收配置。每个真实需求仍须提供业务标准和具体用例关联；范围缺口在记录中保留。


## 交付依据导出

网页任务详情「下载交付依据」、`GET /api/tickets/<key>/delivery`、MCP `webuddy_delivery_get` 和 CLI `webuddy delivery <任务>` 提供同源保存记录。它包含确认稿、测试方案、完整运行产出、基线/候选原始验证、候选评估及人工决定历史。导出不执行 Git、网络探测或验收动作，不将旧结果判成当前有效；进入候选详情实时复核后才按原权限决定。具体接入与私有 CI 配置见 [开发者协作](developer-terminal.md#网页与-mcp-获取同一份交付依据)。

对照《AI 代码可靠性验证方案》：预期应来自已确认规则；基线通过而候选失败先作为疑似回归，结合环境归因。历史失败是否阻断本次交付单独判断。新增功能在基线失败可符合预期。报告读取能力不意味着客户业务已经通过，也不改变项目配置的人工/平台 AI 验收策略。

## 从需求到交付的闭环

以下是执行与留痕规则，不代表每个项目已经完成全部检查。按项目现有配置选择执行、技术复核、业务验收与合并方式，不新增并行状态机。

| 环节 | 实际操作与产出 | 谁决定下一步 |
|---|---|---|
| 需求与范围 | 保存原始要求、规则来源、终端确认稿修订；列出新增行为、旧功能、保持项和范围外事项 | 授权人员确认需求；Agent 不代确认 |
| 基线 | 固定初始提交，在隔离工作树执行可复现检查；新增用例改前失败可以符合预期 | 对历史缺陷与环境缺口分别判断，不虚构绿基线 |
| 实现与候选 | 自动执行或开发者本地修改；核对项目、远端、工作目录、完整提交和未提交差异；登记候选 | 按当前执行授权推进 |
| 实测 | 按项目配置执行构建、测试机脚本、接口／数据库／页面检查；保存逐项输入、独立预期、实际结果及原始报告 | 程序按实际执行回执和现有门禁计算，不由总结文字宣布通过 |
| 独立 Review | 审查实际完整差异及上下文；保留问题、覆盖缺口、执行身份与版本 | AI 判断与指定人员复核分开记录 |
| 返修或受阻 | 业务断言失败进入有界返修；环境或前置依赖受阻先补条件；重复失败按原预算停止升级 | 技术负责人处理问题；此出口不等于业务签收 |
| 业务决定 | 查看当前候选逐项有效依据、未覆盖边界及复核记录 | 人工项目由有权限真人主动确认；已授权 AI 项目仍走原确定性门禁 |
| 合并与发布 | 按项目策略确认合并，再核对正式远端和部署回执 | 本地合并、远端推送、环境发布是三个独立事实 |
| 回测与反馈 | 核对运行版本、认证租户访问、关键业务回测和必要延迟健康；保留失败及返工投入 | 知识沉淀、业务采用与关单继续遵守原权限 |

返修产生新候选后重新判断旧测试及 Review 的有效性。旧报告可读，不等于能支持新候选。检查中变更源码、验收标准、测试配置或相关前提时，不拼接不同版本的绿色结果。

### 浏览器测试、computer use 与 MCP 的区别

| 能力 | 当前实现或检查入口 | 能证明什么 |
|---|---|---|
| 项目测试 | `project_tests.py`、`project_test_runner.cjs`；[配置说明](project-testing.md) | 指定阶段和关联用例在指定候选的实际结果 |
| 测试机 MCP | `testbox_mcp.py`、`testbox.py`；[操作流程](self-improvement/testbox-codex-workflow.md) | 登记测试机收到代码与脚本、执行并返回记录；模拟 SSH 的测试只证明协议逻辑 |
| 产品页面验证 | `browser_verify.py`，项目 `verify-hosts.json` 配置 | 在登记宿主运行 Playwright、逐项断言与截图；没有配置或没有实际运行，不能称页面已验收 |
| 当前开发会话 computer use | 会话实际提供的桌面／浏览器工具 | 需要分别检查应用读取、点击、输入、页面结果和截图；会话可用不等于 Webuddy 自动执行器已接入 |
| 网页与个人 MCP 交付读取 | 任务交付依据与 `webuddy_delivery_get` | 读取保存的产出和证据；读取不执行测试，也不批准、签收或发布 |

产品浏览器结果解释有明确边界：通过但没有截图为未验证；启动、定位、超时或跳过等不能当业务断言失败；有截图的实际断言失败才进入相应失败判断。截图帮助核对页面，不能独自证明数据库、权限和跨系统结果。页面辅助文本有长度边界，不能把它称为完整页面转录。

受限项目客户端 `project_client.py` 的官方 Codex 驱动显式禁用 `computer_use` 等宿主能力，使用项目绑定工具。不要因开发者会话能操作电脑，就宣称该受限驱动可以控制客户桌面；本轮不放宽此边界。

### 每一步怎样留痕

每条操作记录至少包含：时间、实际操作者类型及身份、项目／任务、基线与候选、配置和环境、动作、输入来源、预期、实际回执、退出状态或未知原因、证据路径、下一责任人。凭据不进入记录。终端命令、原始 stdout/stderr、报告及截图保留原件，不以摘要替代。

人工点击、方案确认、Leader 复核、补环境、负责人合并和业务验收分别记实际投入。Agent 在隔离演练中完成的操作明确标为 Agent／合成账号，不登记为客户人工决定。请求超时先查询回执，不能直接重发合并或执行。失败、退出、跳过、未覆盖和失效项一直保留。

可复用[私有仓库全流程演练](../examples/project-testing/jsherp/jenkins-demo/私有仓库全流程演练.md)记录步骤；ERP 演练与怀柔真实项目分开。平台自身测试、客户业务测试、真人验收和价值对照分别形成结论。

### 怎样阅读 CI 与本轮检查

`.github/workflows/ci.yml` 分开运行安装包、快速检查、Windows 执行证据专项、正式 SDK MCP 协议和完整套件。完整套件不自动具备所有可选依赖；MCP 专项另装 `.[mcp]`，执行 stdio、HTTP、租户持久化等测试。协议测试仍包含合成任务及执行替身，不代表真实模型或客户业务。

Windows 完整任务当前配置 `continue-on-error`。因此工作流总体成功也不能证明 Windows 完整通过；取消、跳过和查询失败都不记通过。必须核对完整提交、具体作业、实际用例和运行环境。旧版本 Windows 检查、旧 ERP 业务演练均不得冒充最新版本实测。

本轮最新核对和原始结果见[2026-11-07 测试闭环检查](self-improvement/evidence/testing-loop-20261107/README.md)。

## 本轮场景与成本记录边界

场景材料进入计划修订、子任务正文和检查点契约；变更后重新核验相关证据。记录来源不等于业务确认，FDE 转述、AI 影响建议及冲突处理建议都不授予权限或修改已有门禁。组织知识聚合可提示授权范围内同名不同内容的来源，标为待核对；不是完整政策冲突分析，也不自动选定一个结论。

交付依据新增逐次进程的原始 timing 记录、可获得的用量与 CLI 报告费用。缓存口径不自动累加，真实账单金额未知时保持 null；不能用 MCP 调用次数、平台点数或 CLI 估价充当实际账单。

执行器配置可选 `max_model_invocations` 正整数，与既有 `run_timeout` 一起限制同一运行的模型进程启动。重试也占次数，检查命令不计作模型进程。限额检查和登记在 Runner 锁内执行，达到上限不再启动后续进程，保留停止回执。它约束 CLI 进程启动次数，不约束一个 CLI 内部的全部 HTTP 调用；项目/任务金额预算、跨进程费用预留与供应商账单核对尚未实现，不能承诺“最多2万元”。
