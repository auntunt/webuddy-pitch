# Webuddy 工作区：从任务推进到团队记忆

设计日期：2026-10-22。本文记录产品判断、完整信息架构、状态与动作约定、视觉选择及验证边界。界面设计、已实现功能、真实客户验收分别记录，不能相互替代。

## 1. 本轮要解决的问题

Webuddy 面向软件交付、持续维护与重构团队。用户每天进入系统，需要立即回答：

1. 现在有哪些事情需要我处理？
2. 这件事属于哪个项目、哪个版本，停在哪一步？
3. 谁负责下一步，做决定需要看哪些依据？
4. 这一轮工作留下了什么，其他人下次能否使用？

此前页面已经具备需求澄清、执行、验证、人工复核、知识确认、固定知识引用与经验复用等能力。问题主要出在组织方式：交付、今天、客户、需求、版本、工程并列；知识库、图谱、架构与依据、知识与引用又分散在工程下。第一次进入时需要先理解系统模块，才能找到自己的工作。

本轮将界面围绕工作对象和人的责任重新组织。维护与重构共享项目、任务、证据和知识；它们仍保留不同的流程与验收条件。界面不使用装饰性成功率、大幅宣传标语或模型运行状态来代替业务结果。

## 2. 信息架构

### 2.1 一级入口

| 入口 | 默认问题 | 首屏主体 | 范围 |
|---|---|---|---|
| 工作台 | 现在需要我做什么？ | 待处理队列、当前阻塞与下一步 | 团队范围，可按项目筛选 |
| 项目 | 这个系统处于什么状态？ | 项目列表与选中项目概览 | 单项目身份、版本与工作区 |
| 任务 | 有哪些工作要推进？ | 任务列表、筛选、状态与责任人 | 跨项目查看，操作回到明确项目 |
| 团队 | 工作停在谁手里，如何交接？ | 待复核、待决策、等待外部和交接事项 | 角色与责任，不创建重复聊天产品 |
| 知识与记忆 | 我们知道什么，为什么适用？ | 检索、知识对象、候选记忆与来源详情 | 默认当前项目，显式查看授权来源 |

一级导航在桌面固定于左侧，当前项目持续显示在页头。进入业务对象时，面包屑和对象元数据标明项目，不能仅靠用户记住上一次选择。

### 2.2 具体路由与兼容入口

| 新工作区入口 | 路由 | 旧入口的保留方式 |
|---|---|---|
| 工作台 | `#/workspace` | 原 `#/today` 保留兼容访问；原执行、预览与复核入口继续可达 |
| 项目 | `#/projects` | 项目内提供维护、重构、交付、版本、客户及工程工具 |
| 任务 | 原需求 / 工单路由 | `#/reqs`、`#/tickets`、`#/t/<key>` 不失效 |
| 团队 | `#/team` | 从责任和复核事项进入既有任务、验收与候选页面 |
| 知识与记忆 | `#/memory` | `#/kb`、`#/library`、`#/atlas`、`#/map`、`#/learn` 继续保留 |
| 项目交接 | `#/handoff/<key>`（项目代号） | 与项目知识、既有工单及人工复核证据互相链接 |

运维看板、监控、提效报告、改造计划、依赖清单、智能体运行、外部系统和设置保留为项目的二级入口。减少一级导航数量不等于删除功能。

### 2.3 上下文的层次

```text
团队工作区
  └─ 项目身份
       ├─ 客户与业务边界
       ├─ 当前工作区与代码版本
       ├─ 维护任务 / 重构计划 / 交付
       ├─ 测试、预览、发布与验收证据
       └─ 当前知识 + 固定引用 + 经确认的项目记忆
```

任务和引用记录明确版本，不能随来源 HEAD 前进而静默更新。切换项目不能让旧项目的人工确认自动成为新项目的验收。

## 3. 页面与关键用户旅程

### 3.1 工作台

默认先看需要本人处理的事项，再看等待外部、正在执行和最近进展。每项至少显示对象名、项目、当前状态、下一步、责任人以及等待时间；责任未知显示“待指定”，不能生成一个看似合理的姓名。

待处理应按动作组织，例如“补充信息”“确认范围”“复核结果”“确认知识”，不是把运行失败、客户没回复和待验收混成同一种红色警告。

选择事项后，就地显示目标、阻塞、已完成步骤与所需证据。完整过程和日志仍可深入打开。新建需求继续保留原话与澄清过程，但输入框不能长期占据首屏的大部分高度。

空状态说明下一步：没有项目时连接已有项目；有项目无任务时记录第一项工作；无待办但有执行时显示运行与等待情况。空列表不是“团队已经全部完成”的证明。

### 3.2 项目

项目列表要能区分持续维护、重构、标品、参考资料等角色与工作流，显示当前工作区是否可执行。项目概览汇集目标、版本、待处理事项、知识有效性、最近决策与成员责任。

项目内的维护和重构保留共同的任务与证据语言。重构以目标、范围、依赖和分批验收组织；不能只把普通工单换成“重构”标签。

创建 / 接入项目的结果必须显示登记回执和可用范围。来源不可用、仅供查阅或环境未准备好时，给出明确原因和可执行下一步。不能让本机路径输入框承担整个产品的首次使用说明。

### 3.3 任务与交接

任务详情的阅读顺序固定为：

1. 当前目标、项目与版本；
2. 当前阻塞以及下一位责任人；
3. 主要动作；
4. 验收条件及证据；
5. 本次使用的知识；
6. 变更、运行和完整历史。

一个页面可以保留多个操作，但只有当前可执行的下一步使用主按钮。不能用绿色“完成”掩盖尚未通过的验收条件。拒绝、补充信息、重试、返回上一步都保留理由和已有产物。

交接同时包含“已经做了什么”“还没验证什么”“接下来由谁判断”。阶段产物复核、代码验证、预览可用、客户验收分别显示。

### 3.4 团队

团队页聚焦责任与交接：谁的队列需要帮助，谁在等待业务方，哪些决策阻塞多个任务。普通评论保留在对象上下文，不另造与工单断开的消息流。

界面上的“我”必须由真实登录身份和已记录的责任字段支撑。发起人不自动等于实施人，实施人不自动等于业务验收人。缺失角色显式呈现，不伪造完整组织治理。

### 3.5 知识与记忆

知识列表与选中内容采用同屏阅读。列表优先显示标题、类型、适用项目 / 版本、有效性、确认人及更新时间；完整来源、具体内容与引用关系进入详情。

构建快照、授权、添加来源、对比版本属于管理任务，不与日常检索抢占同一首屏。知识图谱是理解结构的视图，不是所有用户的默认入口。

## 4. 状态与动作约定

下表是界面语义约定。它组织现有事实，不要求把所有后台状态强行改成同一枚举。

| 用户看到的状态 | 必须说明的事实 | 主动作 | 不能暗示 |
|---|---|---|---|
| 待补信息 | 缺哪条需求 / 验收条件，等谁补充 | 补充信息 / 继续澄清 | 已经开始实施 |
| 待决策 | 决策问题、选项与影响范围 | 确认范围 / 记录决定 | 模型已替责任人批准 |
| 等待执行 | 队列原因、运行环境是否就绪 | 查看队列 / 处理前置条件 | 已在后台运行 |
| 执行中 | 当前步骤、开始时间与最近可观察进展 | 查看过程 / 停止 | 业务即将成功 |
| 执行失败 | 失败步骤、完整原因、保留的产物 | 查看原因 / 在条件核对后重试 | 所有工作已丢失或结果全部无效 |
| 待复核 | 产物、测试与未满足的验收条件 | 打开证据 / 逐项复核 | 测试通过等于客户验收 |
| 等待外部 | 等谁、等什么、开始等待时间 | 查看沟通 / 补充答复 | 系统卡死 |
| 已出版本 | 明确版本、包含任务与可用证据 | 查看版本 / 打开预览 | 已部署生产或客户已签收 |
| 已完成 | 符合该对象的完成依据及确认人 | 查看结果 / 复盘 | 所有下游系统都已验证 |
| 知识待确认 | 自动提取内容、来源和适用范围 | 接受 / 编辑 / 拒绝 | 已成为团队规则 |
| 知识需更新 | 使知识可能失效的变化 | 对比变化 / 重新确认 | 历史原文被删除 |

执行、验证、采纳、发布、客户验收至少保持可区分的事实。颜色只辅助理解，每个状态都有文字；黄 / 红状态要带原因及下一步，不只显示警示符号。

## 5. 长期记忆与 automemory

用户所说的“芙蕖”在本轮澄清后指知识库与 automemory 长期记忆，不再作为一个外部项目研究。

### 5.1 五类内容分别管理

| 类型 | 内容 | 可信依据 | 复用边界 |
|---|---|---|---|
| 原始资料 | 代码、文档、客户原话 | 原文、固定版本、来源 | 只在授权范围检索 |
| 项目事实 | 入口、依赖、表结构等解析结果 | 代码版本与解析器记录 | 依赖或配置变化后重新核对 |
| 业务认知 | 规则、术语、流程含义 | 业务确认及原始依据 | 带客户 / 项目 / 版本条件 |
| 决策经验 | 选过什么方案、为什么、效果如何 | 任务、决定、验证与结果 | 保留条件与反例，不只存总结 |
| 团队记忆 | 经审核的通用规则、方法与避坑经验 | 发布记录、来源与审核人 | 共享与引入分别明确确认 |

自动记忆的价值是减少重复查找与交接，不是让系统悄悄扩大确定性。自动提取先成为候选；人工接受、修改、拒绝、撤销或标记过期均有记录。

### 5.2 每条记忆的最小展示

- 内容标题与明确结论；
- 原始依据及可打开的完整来源；
- 来源项目、代码版本 / 知识修订；
- 适用范围与不适用条件；
- 生成 / 确认 / 更新时间及责任人；
- 当前状态：候选、已确认、需更新、不再适用；
- 哪些任务采用过以及相关结果。

“访问过”“被引用过”“被确认过”是不同事实。不能用使用次数替代正确性，也不能因为相同文件未改变而忽略调用关系、配置与业务条件变化。

### 5.3 记忆进入下一次工作的路径

```text
任务与原始依据
  → 提取候选结论
  → 人确认内容与适用范围
  → 存入当前项目记忆
  → 下一任务检索并绑定固定输入
  → 显示本次采用的依据
  → 结果反馈 / 条件变化触发复核
```

跨项目团队经验额外经过脱敏审核、共享授权及使用方引入。现有实现已有固定引用、来源核对、知识确认及跨项目经验的安全边界，界面重组需要把它们呈现清楚，不重复造一套旁路。

当前项目共享边界不等同于完整组织级多租户隔离；未实现的组织治理与细粒度适用性不能通过界面文案伪装成已完成。

### 5.4 可借鉴的长期记忆设计

- [Claude Code Memory](https://code.claude.com/docs/en/memory)：借鉴按项目保留记忆、用户能查看与编辑的方式。Webuddy 中应把记忆的项目归属、来源与人工修订入口放在可见位置。
- [Letta Stateful Agents](https://docs.letta.com/v1-sdk/concepts/stateful-agents)：借鉴持久化状态与当前上下文分开、多个 Agent 可使用明确共享 memory blocks 的思想。Webuddy 中不把所有历史都塞进每次任务上下文，而是按任务需要选取有来源、有效且获准使用的内容。

以上是产品设计参考，不是本轮技术依赖或接入声明。本轮复用自身已有 `learn` 的 `shared` / `taken` / `relevant` 经验链路；未安装 Letta，也未接入 Claude Code 的 memory 存储。

### 6.2 三种方向

三个首屏共用虚构内容，比较的是骨架、阅读路径与主视觉，不拿不同数据制造优劣。

| 方向 | 主结构 | 优点 | 取舍 |
|---|---|---|---|
| A · 接力工作台 | 左导航 + 待办队列 + 当前交接详情 | 批量处理与逐项判断兼顾，当前对象不丢失 | 复杂证据需要进入完整详情 |
| B · 项目调度表 | 顶导航 + 通栏项目任务表 | 横向比较状态、负责人和等待时间 | 窄屏成本较高，适合作为项目汇总视图 |
| C · 证据与交接 | 对象目录 + 主文 + 来源边栏 | 适合知识维护与复杂评审阅读 | 高频处理大量事项不如 A 直接 |

选定 **A** 作为全局方向，延续现有森林绿资产，并与图像模型第一套设计的浅色工作区、稳定侧栏和列表 / 详情关系一致。B 的对齐方式用于调度列表，C 的连续阅读方式用于知识与交接详情；不混用三套字体、色板与控件。

三份 HTML 已由主代理在真实浏览器渲染，设计代理逐张打开保存的全分辨率截图检查。A 能在同一首屏同时展示六项任务与选中任务的交接证据；B 更适合横向调度，C 更适合单个对象的连续阅读。正式采用 A。

### 6.3 样式实现

新增 `tmh/platform/ui_workspace_theme.py`，导出 `WORKSPACE_CSS`，在既有页面 CSS 之后加载。它不修改业务状态、后端权限、模型执行、合并或验收动作。

- 桌面：66px 全局页头、204px 左侧主导航、项目内二级标签、主内容与可选助手。
- 主要字体：中文系统无衬线；27px 页面标题，14px 正文 / 对象名，12–13px 辅助信息；不依赖在线字体。
- 主色：`#21634B`，画布 `#F5F8F5`，内容白色，分隔 `#DFE7DF`。绿色承担主动作与选中态，警告和错误另有文字语义。
- 容器：6–8px 圆角、单层细边，无常规重阴影；对象行优先依靠对齐和分隔组织。
- 窄屏：五项主导航落到底部，二级入口折行，详情依次显示；助手采用全屏面板。完整信息保留，不用缩小整页替代响应布局。
- 新页面可使用 `.ws-head`、`.ws-columns`、`.ws-list`、`.ws-panel`、`.ws-row`、`.ws-stat-grid` 等渐进样式；既有页面继续可用。

### 6.4 动效与反馈

只保留三类短反馈：按钮按下 1px 位移与色彩变化；导航选中背景切换；页面首次出现的淡入和助手展开的轻微位移。状态立即更新，不等待动画。`prefers-reduced-motion` 下取消这些动画与位移。

运行过程、保存回执和失败原因必须来自真实状态，不能用动画制造“正在推进”的错觉。

## 8. 验收要求

### 8.1 首屏与阅读

- 1440px 和窄屏真实浏览器截图中，当前项目、当前页面和主要动作均可识别。
- 第一个工作对象在首屏完整可见；主页面不被说明卡和伪统计挤占。
- 长中文标题、项目名、代码路径、等待原因不会相互覆盖；完整内容有可读入口。
- 100% 阅读尺寸与 200% 放大检查关键文本；不能只看缩略图宣布可读。

### 8.2 导航与状态

- 五个一级入口均可进入；既有重构、交付、版本、客户及工程入口保持可达。
- 项目切换后，对象、知识来源和主要动作确实属于当前项目；历史证据不会假装属于新项目。
- 加载、空内容、错误、等待外部、执行失败、待复核各有明确表现和下一步。
- 已出版本、预览可用、已部署和客户签收不混用。

### 8.3 操作与恢复

- 从实际入口执行到可观察结果；保存后读回，失败后保留输入与当前位置。
- 刷新和后退仍能定位原对象；重试不重复创建业务对象。
- 人工复核保留逐项验收事实与理由；不能一键把未知项写为通过。
- 未接入或不允许的操作显式说明原因，不使用能点击却无结果的主按钮。

### 8.4 知识与记忆

- 用户能区分原始来源、自动推断和人工确认。
- 一条知识可打开确切版本原文，可查看适用范围与确认人。
- 候选记忆可以接受、编辑或拒绝；更新后能重新读取。
- 来源失效 / 授权撤销 / 引用变化时，历史内容保留且当前适用性明确。
- 跨项目复用不继承来源项目的验收，不静默扩大共享范围。

### 8.5 当前记录的验证边界

本设计文档写入时，已完成源码结构审查、基线与两套生成设计板的人工看图、三个首屏原型的实际浏览器渲染与逐张看图，以及主题模块的 Python 语法检查。浏览器中的集成界面验证、真实交互回读和独立评审由集成阶段记录；本节不提前宣称通过。
