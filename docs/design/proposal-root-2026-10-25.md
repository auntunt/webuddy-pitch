# 提案前冻结根预算与一次候选绑定

## 本次解决的问题

旧离线准备合同要求已知 candidate SHA，因此无法直接表达“先冻结全链总预算，再花预算生成候选”。不能先填假 SHA，也不能生成候选后重建合同、重置预算或把旧根合同投影成另一个身份。

本次仅扩展 `scripts/rsi/trial_preparation.py` 内部离线 Ledger。没有新增 HTTP、Store 启动迁移、模型调用或生产执行入口。旧 v1/v2 的字段、四张表 DDL、状态序列及现有适配器协议保留。

## 不可变身份

- 新 schema `trial-budget-proposal-v3` 在提案前冻结原合同。`candidate_sha256` 必须为 JSON null，之后仍为 null；原合同全文、摘要、代际、创建时刻、总额度、原期限均不更新。
- 只允许 `propose` 阶段在未绑定状态预留。每次预留必须绑定完整输入材料摘要；intent 使用原 FULL/持久日志门。
- `bind_candidate` 引用同根已结算提案的 request、intent、body、receipt、raw response 摘要，保存完整候选策略原文和 UTF-8 SHA（不去除首尾空白或换行）。候选须不同于原基线。
- 单独 append-only `bind_candidate` 根事件记录这份声明。所有后续非提案阶段的预留同时引用原合同摘要和该绑定摘要。原提案预留仍引用原根，不能回写成后生成候选。
- 绑定后不允许新提案；已有完全一致的绑定只能只读重放，任何换候选、换提案或换原响应都拒绝。代际变化后只能读历史，不能恢复新派发。

## B/C 消费、事务与预算

绑定与原合同预封 B/C 全集合的 claim、唯一 `consume_holdout` 事件在同一既有事务内完成。中途任何插入失败，绑定事件、全部 claim、消费事件和时刻更新一起回滚。相同项目中两个不同根竞争相同集合，至多一根绑定成功；不同项目保持原有范围独立。

预封集合在绑定时即消费。即使后续没有执行，也不退回、换候选或重新抽样；这比等待首笔终测才消费更保守。不能单独消费一个 null 候选来占位。

提案与所有后续阶段复用同一个 `_totals`、累计调用数、Token、费用上界和原截止时间，不另建预算。本轮人类给出的 **20 元是全阶段、全模型与全部重试的一个根总额**，不是每次调用或每阶段 20 元；内部通用 Ledger 不把这一特定试点金额硬编码成所有未来项目预算。价格必须来自可信绑定，本离线数值测试不证明实际计费准确。

预留、意图、unknown 或未解决隔离会阻断新绑定。未知仍保留最大预留与根阻断；迟到的已知结算不会重开原根。已有候选绑定后来遇到原回执框定无效时，保留原绑定及消费历史，恢复最大费用预留，禁止继续派发或重结算。

读回同时检查原 create、提案 reserve/intent/settled、候选绑定、集合消费与 claim 的一致性。缺锚、缺 claim、删除消费、尝试换根/换绑定均拒绝，不自动修复或回填历史。这是原可信本地数据库内的一致性保护，不抵抗管理员同时重写整套账本。

## 明确未闭合的信任边界

**原响应摘要引用不是“候选确实由该响应产生”的证明。** 这里记录的是可信调用方提交的完整候选声明，`candidate_derivation_verified` 始终为 false；`execution_authorized`、`provider_evidence_verified`、`os_holdout_isolation_verified` 仍为 false。

旧 provider adapter 明确拒绝新 schema。后续接线须从保全的真实原响应提取策略，验证完整文本与摘要，再统一使用已冻结 selector/renderer 进入未见 B/C、本人采用及新 D；不能仅凭 `candidate_bound=true` 放开执行、收费或宣称 RSI 完成。Responses/Messages 实际协议、可信全费用上界和执行工具合同仍需单独收口；本次真实模型/付费为零。

## 验证范围

新增测试覆盖合同不变、完整原文、原回执引用、预算跨阶段累计、一次消费、同根幂等、同库与两连接并发、不同根争同一集合、两处插入故障回滚、代际/期限、原 unknown 和坏框定晚结算、缺失/改绑账本以及旧 adapter 拒绝。原测试断言、原四表 DDL、监管/超时阈值、guard 与人工确认规则未修改。
