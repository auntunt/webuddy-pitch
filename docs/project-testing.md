# 项目测试

在“设置 → 项目 → 项目测试”配置项目自己的检查。自动修改和手动“运行测试 / 测试并 Review”共用此配置。只有平台管理员能修改执行命令，成员按项目权限查看结果。

## 如何接入

1. 选择执行位置。SSH 测试机沿用“设置 → 测试机”；本机使用平台的运行环境。两处需要 Node.js 运行平台的无第三方依赖适配器，项目依赖由准备阶段安装。
2. 按项目需要配置准备、构建、静态检查、单元、集成、端到端、安全、性能、数据迁移、变异测试和清理阶段。阶段依次执行；依赖填写前面阶段的代号。清理即使依赖失败也执行。需影响交付的阶段勾选“必需通过”。
3. 单元、集成和端到端测试必须产出 JUnit XML 或 JSON 用例报告。报告路径相对于项目工作树，可用 `*` 匹配一级文件名，如 `target/surefire-reports/TEST-*.xml`。多模块可以分别配置阶段。报告应放在项目 `.gitignore` 已排除的输出目录；测试改动源码或生成未忽略文件时，原版本检查会阻断通过。
4. 配置验收项与精确用例 ID 的关联。例如 `{"A1": ["orders.OrderTest::rejectExpiredOrder"]}`。JUnit 用例 ID 为 `classname::name`，无 classname 时只用 name。运行结果中可查看实际 ID。一个绿的套件不能代表所有验收项。
5. 保存后，对已有改动点击“运行测试”。查看各阶段、用例、完整日志、未覆盖项和证据位置。修改配置会使旧验证失效，需要重跑。

JSON 报告格式：

```json
{"cases": [{"id": "orders.rejectExpiredOrder", "status": "pass"}]}
```

状态仅支持 `pass`、`fail`、`skip`。报告必须由测试框架的真实断言结果生成。缺报告、旧报告、零用例、重复用例身份、失败或跳过不能算该阶段通过。命令返回 0 不覆盖报告里的失败。

## 典型检查

| 项目 | 检查命令示例 | 报告 |
|---|---|---|
| Maven | `mvn -B test` | `target/surefire-reports/TEST-*.xml` |
| pytest | `python -m pytest --junitxml=reports/unit.xml` | `reports/unit.xml` |
| Vitest | `npm run test -- --run --reporter=junit --outputFile=reports/unit.xml` | `reports/unit.xml` |
| Playwright | 项目中配置 JUnit reporter 后执行现有 e2e 脚本 | 项目配置的 XML 路径 |
| 类型 / 构建 | 项目已有的类型检查、lint、build 命令 | 以退出状态为准 |
| 安全 / 性能 / 迁移 | 项目已有工具，命令须在违反阈值时返回非零 | 可追加用例报告 |

这些是配置示例，不会自动安装测试框架，也不会替没有测试的业务生成“通过”。安全扫描规则、性能阈值、迁移数据集和变异测试强度需按实际项目选择。缺少业务场景时，平台不能推断项目已被完整覆盖。

## 交付规则

- 项目测试证明当前候选的结果，不自动证明原版本通过。原版本基线没有实测时保持未知；仅单元测试通过，也不自动标记独立构建通过。原有基线确认规则保留。
- 至少配置一项必需的单元、集成或端到端测试。必需阶段失败阻断技术采纳；原有 AI Review、权限、人工签收和业务状态规则继续执行。
- 打开“要求每项验收标准都有通过的用例”时，没有标准或标准缺少对应通过用例会阻断项目测试。
- 依赖命令失败时不执行后续依赖阶段；报告解析才发现的失败也会使后续依赖结果不能用于交付。清理阶段独立收尾，必要清理应设为必需。
- 精确基准版本和完整补丁发送到测试机，每次执行使用隔离目录。原始报告和日志保留字节、摘要与执行配置；报告丢失、内容变化、配置变化或验收标准变化后，旧结果不能继续采纳。
- 本次项目用例关联展示在运行验证页。原有工单页面实测、人工复核和签收规则不被这些用例自动替代。没有配置的项目明确显示没有项目测试报告，不称为完整测试通过。
- 准备/清理命令负责项目服务和外部测试资源。阶段超时会结束该阶段进程树；业务级清理应编写成可重复运行的命令。SSH 中断时无法取得完整结果，不能算通过。

## 审查参考

借鉴 [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/) 的分层检查、具体缺陷证据、有限复审与可恢复交付。代码 Review 要求文件与行号、触发条件、影响，并区分新问题和旧问题。机器测试、AI 判断和人的决定分别呈现。
