# Webuddy 能否承担日常开发：历史工作核对

评估日期：2026-10-19。平台依据版本：`cfbed01997201bb59963b16ced9e5635afd1b4fa`。本轮交付是实用性评估、历史任务样本和新执行的回归证据，没有新增业务功能或生产发布。

**结论：可以开始由你监督的日常开发试用；还不能据此认定它是已验证的组织级开发平台。** 最适合先承接已有代码库中的明确功能、缺陷、接口和数据流程修改。它已有固定代码版本、执行期限、失败恢复、独立验证、预览、验收和 CLI/MCP 的基础。当前完整证据集中在本地 BOOTV2，其他项目的接入可靠性、多人权限和实际节省工时还要通过真实任务验证。

**产品边界已按你的最新要求调整：Coding 独立。** Codex、Claude Code、Cursor、Git 仓库与 Webuddy 构成开发工作入口。WorkBuddy 主要用于办公，不要求同步，也不把办公集成作为 Coding 的上线条件、提效前提或下一轮必做项。开发过程中需要的需求说明、测试报告、交付文档仍属于 Coding 范围。

## 现在最影响实用性的四个缺口

**1. 从一个样板到多个真实仓库的接入。** 不同项目需要不同构建、测试、数据库、预览及交付方式。BOOTV2 的本地 SQLite 路径不能直接代表 PostgreSQL、多服务、私有媒体和移动端。应将项目入口、固定基线、验证命令、数据准备、预览与清理做成项目配置，并让第二个真实仓库走完外部 Agent 候选链路。已有超时和故障恢复继续复用。

**2. 多人使用的身份与权限。** 当前 Agent 名是审计标签，共享服务令牌及进程级读写开关主要适用于可信本地工作区。它们还不足以表达团队成员对某个仓库、某个项目、某类操作的授权与撤销。CLI/MCP 不开放最终人工批准已有意义，但同一系统账号可读的本地操作者凭据不构成组织级隔离。需要独立的开发身份、项目范围、最小操作权限和审计；不依赖办公系统同步。

**3. 减少实际需要人接手的步骤。** 真实 BOOTV2 过程中，Codex 的沙箱监听和 Git 元数据权限导致部分测试、提交由协调者完成；客户端 MCP 审批也出现过真实拒绝。消息目前通过持久收件箱拉取。应将这些介入记录为可处理的阻塞，改进受支持的本地执行环境、客户端接入和回执恢复，不能把协调者补做的工作统计为无人完成。

**4. 提效账还没有闭合。** 目前 `tmh/platform/metrics.py` 的关闭口径主要读取旧工单 `accept` 事件，新候选验收保存在 `candidate_decisions`。本轮只读快照里，BOOTV2 有同一候选的两条验收历史、没有旧 `accept` 事件。两条历史不能算两个完成任务；候选批准也不等于关闭工单。应保留两者语义，并补充“按确切版本验收的交付”统计。

现有 `human_actions` 是动作次数，不是人工投入分钟；点数乘单价也不自动等于外部 Codex/Claude 的实付费用。缺少封存基线时不出比较数的规则应保留。目前没有可用证据回答“省了 30% / 50%”，也不宜据此计算组织 ROI。[只读统计证据](evaluations/daily-coding-2026-10-19/metrics-observation.json)

## 独立 Coding 产品应当怎样落地

日常入口使用开发者已有的 Codex、Claude Code 或 Cursor。Webuddy 保存同一份需求、验收条件和版本化交付记录，提供受管执行、独立验证、可打开预览及失败恢复。Git 与现有 CI 继续承担源码协作和已有检查。人工在范围、重要风险、业务验收及已有授权要求的位置决策。

第一轮选择**磅单系统的一条明确业务修改**，完整经过 CLI/MCP 需求 → 外部 Agent 候选 → 独立测试 → 独立数据预览 → 技术观察 → 你的验收。原图保真、业务来源隔离、原数据保持作为必守条件。第二轮选择集团数据收集系统，检验“多公司权限＋导入导出＋数据迁移”能否稳定复用这套流程。具体新业务变更应取真实待办；本轮没有擅自发明客户需求或执行数据库迁移。

对你已有的 WhatyTerm、unmanned-factory、webuddy-core/console 等开发项目，先确认哪个承担当前功能，复用有效能力和已有 CI，避免同时维护多套不一致的候选、运行与验收协议。WorkBuddy 不参加这项 Coding 整合。

## 如何证明它值得推广到组织

以下是**建议的试点设计，尚未执行或获得结果**：你与 2–3 位开发者，在 2–3 个真实仓库完成首批约 20 个范围明确的任务，覆盖功能、缺陷、数据/权限及交付文档。先试 10 个工作日，返工指标继续观察到每个任务验收后的 14 天；样本不足时不外推到全组织。

对照的是“相同编程助手直接开发”与“相同编程助手＋Webuddy”。尽量保持模型、预算、环境与验收条件相同；按难度匹配任务并交错分配。历史已完成任务用于回归时，代理只拿修改前版本和当时需求，最终补丁与独立验收答案隔离，避免抄现有解法。新的真实任务用于验证日常实际收益。

| 必须记录 | 判断方式 |
|---|---|
| 人实际投入的分钟 | 包含说明需求、环境准备、审阅、手工补救、返工，以及分摊的平台维护；重叠计时去重 |
| 从明确需求到验收的耗时 | 同时报告总周期与外部等待，不用模型运行时长替代 |
| 每个验收任务的真实成本 | 有实际账单依据才记费用；无法归因的订阅费用单列，缺失保持未知 |
| 独立业务验收与返工 | 构建、测试、数据完整性、权限和可运行产物都核对；14 天返工按成熟样本统计 |
| 失败、放弃和人工介入 | 全部纳入分母，说明卡在哪里，不只统计成功样例 |

可把“人工投入中位数减少 30%，业务验收不退步，试点内无严重数据/权限事故”设为内部试用目标。30% 是拟定目标，不是已测提升或行业保证；样本分布、失败和不确定性都要同时展示。条件不足就继续限定范围，不把试点通过描述成全组织稳定性保证。

这与 Anthropic 对 Agent 评估的建议一致：核对环境中的实际结果，同时记录过程与成本，并区分已知行为回归和新任务能力。来源为 2026-01-09 发布、2026-10-19 查阅的 [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。它提供评估方法，不能替代我们的收益数据。

本轮留下的案例清单是后续接入与回放的候选集，未设置自动执行，也未把文档中的历史“通过”升级为本轮通过。下一步优先完成第二个真实业务仓库的完整交付，同时开始记录人工介入与成本。
