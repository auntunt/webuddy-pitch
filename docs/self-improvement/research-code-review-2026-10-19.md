## 来源与适用边界

1. [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/)，Addy Osmani、Morgan Westlee Lunt、Qing Wang，2026-10-15。这是团队工程实践文章，不是经同行评审的实验论文。
2. [Redesigning source control at Anthropic](https://www.anthropic.com/engineering/redesigning-source-control)，2026-10-13 发布、2026-10-15 更新。已在 [上一份研究记录](research-2026-10-18.md) 收录，本次补充两种仓库流程的区别。

第一篇报告 Claude Code 自身代码约九成由 Claude 编写，6—9 月合并 PR 数超过翻倍、回退比例下降超过 40%；这是团队自报的前后观察，不能推出 AI 审查单独造成改善，也不代表所有缺陷下降。第二篇的每天约 2,500 → 超过 30,000 次合并属于 Anthropic 单仓，不能归到 Claude Code 独立仓库。[来源 1](https://claude.dev/blog/solving-code-review-at-anthropic/)、[来源 2](https://www.anthropic.com/engineering/redesigning-source-control)。

Claude Code 的方案包括实际自验、独立审查、安全检查、按风险人工批准、合并队列和渐进发布；低风险简化审批还受可信作者及敏感路径限制。审批绑定具体提交，AI 不能代替必要的人工审批。复审三轮后应重新考虑方案，后续关注增量且不重复已报问题；用事故样例与已知干净样例同时衡量漏报和误报。[来源 1](https://claude.dev/blog/solving-code-review-at-anthropic/)

Scion 超大单仓侧重合并后、部署前的自动检查，并未采用同样的全局合并队列；它的规模和资源条件不适合作为本项目默认架构。Webuddy 继续使用 Git。[来源 2](https://www.anthropic.com/engineering/redesigning-source-control)

文稿中的“一轮通过 65% → 78%”“五轮以上 8.9% → 1.5%”未出现在本次取得的正文文本中，图表值尚未独立核验，不纳入已验证指标。来源本身也不构成 Webuddy 降低审批要求或自动发布的授权。

## 后续实施顺序与验收约束

继续优先处理 SI-010 已复现的全页刷新草稿丢失。之后按真实阻塞选择 SI-011 审查收敛，不因新增参考重复建设已完成的进程恢复、版本绑定或证据失效机制。

SI-011 的最小完整路径建议：一次候选提交产生审查意见 → 保存稳定的问题编号、严重程度、具体版本/位置与复现证据 → 修复或附理由处置 → 对新差异复审 → 同一问题不重复触发改码 → 到达轮次或时间预算时保留现场、明确重新规划/人工决策入口。已知旧缺陷可另立事项，但新暴露的严重问题仍需阻止交付。意见关闭不等于行为修复，不能替代确定性失败检查。

审查评估与产品回归分开：错误基线应能被检查发现，修正版本应通过相同业务断言；干净对照不应被建议改坏。固定模型/提示词/工具/代码版本和样本，保留全量结果及失败原因；先建立基线再决定是否采用策略。记录首轮通过率、有效问题、漏报、误报、轮次、人工介入及可取得的耗时/成本，未取得的值保持未知。提交数、评论数、测试数、代理票数都不是修对率。
