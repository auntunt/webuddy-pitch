# 原验收技能案例记录（内部保留）

## 反模式清单（来自 JeecgBoot 40 张真实工单和官方修复的对照评审）

那轮评审的结果：与官方一致 8 张，思路一致 10 张，**方向对但改太多 7 张**，改法不同需验证 9 张，**方向不对 6 张**。下面每条都是一张真实工单的教训，作为检查项：

**改太多（找对了地方，改动远超需要）**
- [ ] 缺接口类问题，是否照着已有的同类接口补齐？（JB-6：缺 `/sys/user/addTenantUser`，官方三十几行照着新增用户补齐；模型加了一串新校验和几百行测试，改了 346 行）
- [ ] 报错位置明确时，改动是否就在报错处？（JB-25：空数组取 `[0]`，官方一个可选链 `validTabList[0]?.path` 就修好）
- [ ] 是否改了公共工具类或共用组件？没有必要就退回。（JB-34：官方只在 `saveUrl` 不为空时用它做目录，6 行，不该改公共的 CommonUtils；JB-13：官方只在弹窗打开时 cloneDeep 已选值，不该重写共用组件）
- [ ] 是否只删掉/改掉了出错的那一处数据合并或赋值？（JB-9：主表编辑误删子表，官方只删掉把分页后的子表数据合并进主表的那一处）
- [ ] 是否新增了测试文件而项目这次并不跑测试？（7 张已改完的单里 4 张自己补了测试文件，审阅成本翻倍）

**方向不对（根因不在模型改的地方）**
- [ ] 根因有没有证据？没证据的“根因”不能当通过。下面几类根因常在业务代码之外，先排除：
  - 依赖版本不兼容（JB-16：Swagger 接口错位是 knife4j 4.6.0 与 springdoc 不兼容，官方回退到 4.5.0）
  - 容器或框架的配置上限（JB-19：批量删除几百条失败，是请求参数个数超过 Undertow 上限，官方在 UndertowConfiguration 调大）
  - 组件自己的解析逻辑（JB-10：编辑器打不开，官方只在“首尾是花括号就当 JSON 解析”处加 try/catch）
  - 设计器或前端的异步覆盖（JB-12：树表添加子记录变成主记录，根因在表单设计器 CgformModal 多个表格异步同步互相覆盖）
  - 判断条件写错（JB-23：`indexOf('_dictText')` 没和 -1 比较）
  - 性能问题来自重复计算（JB-27：列变化时反复重建列，官方给 watch 加 50ms 防抖）
- [ ] 改动是否跟着提报人猜测的原因走、却没有复现证据？是的话退回，要求先在契约里写出证据。

**假绿**
- [ ] `tmh accept path-check` 是否通过？“平行实现”（新方法/新类没接上入口）一律退回。
- [ ] 测试是否在测新写的那套，而不是入口真正调用的那套？
- [ ] mock 掉的部分是否正好是这次要修的部分？
