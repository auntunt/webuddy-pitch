# Codex 在测试机验证改动

平台的 Codex 修改任务使用已有测试机 SSH 连接，通过两项运行专属 MCP 工具完成验证：

1. `testbox_info` 查询测试机系统、工具和本次独立目录。
2. Codex 在当前代码目录编写测试脚本：Windows `.ps1`，Linux `.sh`。
3. `testbox_run` 同步当前提交与全部未提交改动，在测试机运行脚本。
4. Codex 根据退出码和日志修复，再测试。平台仍运行原配置的构建检查及独立诊断。

脚本负责安装项目依赖、构建、自动化测试。涉及运行行为时，还需启动本次应用，等待健康接口，并检查需求涉及的接口或页面；使用独立端口、测试数据，并在 finally/trap 中清理自己启动的进程。外部依赖或数据不齐时必须明确失败，不能打印 OK 代替验证。

不需要把 SSH 私钥交给模型，也不关闭 Codex 沙箱。工具只能使用服务端已配置的测试机，绑定当前运行和工作目录；不是任意主机 SSH 入口。个人隔离执行路径不因此开放宿主机能力。现有人工验收、采用和发布要求保持。

测试目录按租户数据目录摘要和运行号区分，避免不同任务互相覆盖。Windows 测试脚本有远端超时看护：到期终止该脚本进程树；正常退出时脚本仍须负责清理其启动的服务。

每次回执保存在 `runs/<运行号>/testbox/`，包含脚本命令、基准提交、完整改动摘要、退出码和完整日志。运行页面同时记录测试步骤与回执编号。最后一次有效回执必须对应当前代码；缺少回执、失败、未完成或代码变化均不能得到本轮测试通过。脚本通过只证明实际执行的检查，不代替逐项业务验收。

后台 Codex 为这两项已授权工具单独设置 `tools.<tool>.approval_mode="approve"`；不修改全局审批策略。依据 [OpenAI Codex 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference) 的 MCP 单工具审批字段。首次实测在默认策略下被拒绝，不能把工具已列出当作调用成功。

## 与桌面操作的边界

本流程是登记测试机上的代码同步与脚本执行。`testbox_run` 返回成功不等于 Windows 桌面点击、浏览器业务操作或真人验收已经完成；页面操作需要对应的实际浏览器脚本和断言，桌面操作需要另有可用且获授权的宿主能力。当前开发会话的 computer use 不自动授予平台执行器相同能力。统一闭环和逐步留痕要求见[验证与 Review](../verification-review.md#从需求到交付的闭环)。
