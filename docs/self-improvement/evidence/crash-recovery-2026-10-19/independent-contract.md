# 独立服务崩溃恢复合同

基线：`0428c1ca771f0d53f54310806fd782e99675ab78`。测试文件：`tests/test_crash_recovery_independent.py`。只使用测试创建的临时 Git 仓库、Store、随机回环端口服务和已知进程，不操作现有平台实例、8792 或生产。

2026-10-19 首次实际运行 3 项：1 项通过，2 项失败，完整原始日志为 `independent-red.log`。每项的 Store 行、lifecycle、attempt 原始文件字节（Base64 无损保存）、进程 ps 状态和清理前后证据位于 `independent-red/`。

测试运行一个真实回环 HTTP 服务。该服务调用真实 `Runner.run_command`，被管理程序派生同进程组子进程，两者忽略 SIGTERM。测试确认原始二进制输出已被服务接收、工作区中间修改已写入、子进程已运行之后，只对测试持有的服务 Popen PID 发 SIGKILL。程序进程组与服务进程组、测试进程组均不同。

失败事实：

- 第二个 Runner 的 `recover()` 把仍由活跃服务拥有的 running 记录改为 failed；原服务及受管程序仍在运行。
- 服务被 SIGKILL 后再调用 `recover()`，受管 leader 与 child 仍执行；lifecycle 未结束且没有中断原因/完成回收回执，已发出的原始 `00 ff` 字节没有 `output.bin` 记录；普通运行永久停留在无法续跑状态。

旧 PID 回执的负例通过：只写入旧 pid/pgid（指向测试另行启动的无关进程）不构成终止授权；该进程仍活着且续跑保持 blocked。

待实现必须满足的行为：

1. 服务父进程消失后，本次程序及同组子孙实际退出；保留已接收原始输出、已写代码和失败原因。不能以退出码、状态字符串或最终 JSON 自称回收成功。
2. 恢复只认可信的本次运行持有关系与完成回执。旧 PID/PGID 不能直接用于重启后的 kill；缺失或不匹配的所有权证明应明确 blocked。
3. 第二实例不能抢占仍活跃的运行，也不能把它误标失败。
4. 回收完成后普通运行可以由真实 `Runner.retry` 重新启动测试专用本地 checker，checker 必须实际读到完整中间修改；原仓库 HEAD 和原中间字节保持不变。
5. 重复恢复不篡改历史回执。隔离测试清理必须与产品回收分开记录，不能把测试兜底 kill 当成产品成功。

风险边界：父服务强杀时不能依赖 Python finally；pipe EOF 需要确保子程序没有继承保活写端；监督器持有的 Popen/组关系与耐久完成回执需绑定本次 attempt；跨实例持有锁必须不被子进程继承；nonce/回执验证失败不能静默补造 cleanup=true。签收或模型正确性不在本回归范围。

首次失败后的残留进程已由测试按精确临时脚本路径再次核对后逐 PID 清理，读回所有本次 worker 均已退出。清理动作与原始失败结果独立保留。
