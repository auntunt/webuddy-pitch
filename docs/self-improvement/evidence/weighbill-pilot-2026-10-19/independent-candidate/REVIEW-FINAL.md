## 发现并修复的问题

**P2：重复读取最新记录的迟到响应能覆盖已经确认的新版本比较表。** 在 `8da19e0` 的 `readLatest()` 中，请求只检查记录 ID 和 conflict 对象，没有区分同一核对会话里的多个请求。独立脚本安排两次真实控制函数调用：后一次先返回 v2，用户明确确认 v2；先前请求随后返回 v1，把 `session.latest` 与比较表换回 v1，而 `reviewed=true`、保存条件仍为 v2。这样比较表中的“采用最新”会提供旧字段，可能在有效 v2 保存条件下覆盖更新。

原始失败断言是 `latest.version` 的 `1 !== 2`，完整证据位于 `report-controller-first.json` / `.log`。主代理修为递增 `readSequence`，成功与错误分支均验证当前记录、conflict 会话和读取序号。最终提交执行原独立 8 场景全部通过。只读复核也确认新增产品回归覆盖迟到成功、迟到 503 和切换记录后的迟到 503，未删除原草稿、审核版本及错误处理断言。最终差异保存在 `final-race-fix.diff`。

## 验证的业务行为

- 两个客户端同读 v0，B 保存新重量后，A 的旧全量表单得到 409；记录、数据库版本和历史保持 B 保存后的状态。
- 旧页面审核不会批准未见的新重量。混合批次只批准版本匹配的记录，过期/非法版本逐条 skipped，其记录和历史不变。
- 丢失保存 ACK 后重发相同条件受到 409 保护，不会覆盖期间他人的更改。显式重新核对后的合并保留 B 的新重量与 A 有意改的货名；随后按成功响应的新版本审核。修改已审核记录后，重新回到未审核。
- 显式 null、布尔、字符串、浮点、负数及容器版本不能降级为无条件写入；合法 0 可使用。缺失审核映射键逐条拒绝。非审核员保持 403。
- 两个独立服务实例在同步读到同一版本后竞争写入，只有一个 200，另一个 409；只发生一条有效修改历史，底层 CAS 没有被替代或移除。
- 独立页面函数验证保留完整草稿、拒绝核对确认时不能提交、未知 ACK 加读取失败不能重放、不完整保存回执不能接着审核、审核使用 PATCH 返回版本、部分成功显示 skipped、拒绝审核不能跳到下一单，以及新旧读取隔离。
- 非空完整前缀下实际访问采集页、台账页、直接静态 HTML、CSS、Service Worker、详情、历史及 CSV。根 API 不会意外开放。非白名单 Origin、null、cross-site 及伪造转发 Host 拒绝；同源写入正常；精确允许的本机预览 Origin 仅在真实回环客户端条件下有效，非回环客户端拒绝。
- 专用预览首次只生成三条合成记录；保存后重启保持记录、版本与历史，标记内容不变。三个生成原图经实际文件接口读取，字节数和 SHA-256 与生成标记一致。无预览标记的非空目录、根符号链接、错误标记均在改变测试目标前拒绝。没有测试或接触真实业务数据目录。

## 边界和保留事项

- 页面脚本场景使用真实发货函数配合隔离 DOM/fetch，不能替代协调者最终候选的实际浏览器操作和版本化预览验收。
- 所有用户意图合并仍需明确核对当前全量表单；没有自动冲突合并。草稿保留在页面内存，关闭提示不等于崩溃后持久恢复。
- 条件协议在旧 API 中可选；作废、恢复、疑问标记等不在本轮版本条件范围。部署身份依赖原有可信网关/本地设置，本报告没有验证生产认证或扩大其授权。
- 预览的目录标记用于防止常规误用，不能视为能抵御同机有文件写权限者伪造标记的安全隔离。真实 OCR 在预览中关闭，没有把合成数据流程称为已接入现场识别。
