# 称重台账多人编辑：独立业务缺口复核

结论：发现一个已用真实 HTTP API 和隔离 SQLite 复现的高价值缺口。**客户端所见版本没有进入写入条件；两位审核员打开同一张单后，后提交的旧全量表单会无提示覆盖前一个人的修改。** 同一缺口使旧页面可以审核通过未看过的新重量，并使保存回执丢失后的重试再次覆盖他人修改。建议将本轮外部候选限定为“详情编辑 → 冲突保留草稿 → 核对最新值后重试 → 按当前版本审核”这条路径。

## 实际失败

三个场景各自使用全新的临时 SQLite 和明确标识的合成台账记录。记录由测试直接植入合法业务状态，之后读、改、审核、历史查询均调用实际 FastAPI 路由和产品服务。没有伪造 PATCH 成功或存储结果，没有访问原仓库的 `data` 或备份库。注入的 ScriptedVision 没有任何调用，不涉及 OCR 模型或签名框选。

| 场景 | 请求与结果 | 业务影响 |
| --- | --- | --- |
| 两人编辑 | A、B 都读到总重 11000、净重 1000；B 改为 10900/900，返回 200；A 只想改货名，但页面全量请求带着旧重量，仍返回 200，最终变回 11000/1000 | B 的有效重量修正被无提示覆盖 |
| 旧页面审核 | A 看过净重 1000；B 把净重改为 900；A 按页面现有协议只提交记录 ID 审核，接口接受，最终 900 被标为 approved、审核人 A | A 审核通过的是自己未见过的新数字 |
| 保存回执丢失后重试 | A 改货名已提交成功，但客户端未使用回执；B 再把净重改为 900；A 重发相同旧表单，返回 200，净重回到 1000 | “再点一次”可能破坏保存后的其他人修改 |

第三个场景明确建模了“服务已提交但客户端未收到/使用 ACK”，没有声称真的在浏览器中断网。所有 API 请求和返回都是真实执行的。测试脚本退出 0 表示这些缺口被成功复现，不表示业务通过验收。

修改历史也提供了直接证据：`stale-edit/result.json` 中先记录 reviewer-B 的净重 `1000 → 900`，随后 reviewer-A 的 `900 → 1000`。因此当前留痕确实记录了覆盖，而不是后台把 B 的提交回滚或漏记。`stale-approve/result.json` 则记录 B 改重量后，A 的“审核通过”。

## 精确位置和原因

- `weighbill/static/report.html:1019` 优先使用列表缓存记录打开详情，`1024` 保存表单快照。
- `weighbill/static/report.html:1144–1146` 在修改任一字段时发送全部 `FIELDS` 以及类型、客户、来源；没有客户端读版本条件。
- `weighbill/http_api.py:344–345` 的 v1 PATCH 不读取或传递预期版本。
- `weighbill/service.py:659` 每个保存请求重新读取当前数据库记录；`664` 再把客户端旧字段合入。因此后提交者使用的是服务端刚读到的新 version，旧客户端数据仍能成功写入。
- `weighbill/service.py:917–942` 的 `record_view` 不返回已有的 `Record.version`。
- `weighbill/adapters/store_sqlite.py:140` 的 `UPDATE ... WHERE version=:version` 本身正确，它保护的是一次服务调用内部的读写窗口。它不知道浏览器打开表单时看到的版本。现有 `tests/test_concurrency.py` 和 `tests/test_multi_instance.py` 主要覆盖服务端窗口竞争，不能替代长时间打开页面的两个客户端场景。
- 审核同样只有 ID：`report.html:659` → `http_api.py:321` → `service.py:714/726`，会读取并批准当前记录，没有核对用户实际看过的版本。

## 页面失败与重试的独立检查

`reproduce-report-retry.js` 提取原页面实际发货的 `act()` 函数，用隔离 DOM/fetch 夹具依次返回网络错误、409 和成功。Node 执行通过，行为记录在 `report-retry-handler.json` / `.log`。

- 网络错误后表单草稿保留，按钮重新启用。
- 409 也进入同一个 catch（`report.html:1160–1162`），显示“修改还在，可以再点一次”，没有核对最新值的分支。
- 连续三次提交发出完全相同的旧全量重量；错误后、成功前没有重新读取记录。

这只是实际处理函数的隔离执行，不是完整浏览器验收。它与真实 API 的旧值覆盖复现相互补充：单纯保留草稿和再次发送，并不能构成安全的失败重试。

## 建议该候选的验收边界

1. A、B 从同一版本打开；B 先保存，A 再保存必须明确报告冲突，B 的字段和版本保持不变，不新增一条声称 A 修改成功的业务历史。
2. 冲突保留 A 的完整草稿，提供最新内容与差异；在核对后重试，只采用用户确认的变更，不能把未改的旧重量自动覆盖回去。成功后历史包含准确操作人和真实前后值。
3. 网络失败与回执不确定要可恢复。重试必须受版本或幂等约束保护；不能重复覆盖期间发生的修改或把未保存说成已保存。失败前的草稿不能消失。
4. 修改后审核及未修改直接审核均绑定用户确认的版本；别人更新后，旧页面审核不得通过。核对新版本后可以继续审核，成为一个可完成的用户流程。
5. 保留现有单请求/多服务端 CAS、权限、已审核记录修改后回到未审核的行为。兼容接口的缺省版本策略应明确，不能因为旧入口仍可盲写而把保护宣称覆盖全部客户端。

未扩展到签名、OCR 或其他产品改造；未接入项目配置、远端或生产，避免与主代理重复工作。
