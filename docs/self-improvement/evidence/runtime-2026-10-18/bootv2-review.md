## 一项具体发现：换行标题的长度口径不一致

优先级：P2。影响已有 A1/A2 的标题编辑边界，不涉及新增产品需求。

`app.py:64` 的编辑控件为 `textarea maxlength="200"`。`app.py:160` 在收到表单后直接用 `len(raw_title) > 200` 拒绝标题。编辑控件中的换行通常表现为 LF，而原生表单提交会把换行序列化为 CRLF。服务端将一次换行计为两个字符，导致界面上没有超过限制的标题保存失败。

本次隔离 HTTP 复现使用同一事项、done=1：

| 输入与步骤 | 实测结果 |
| --- | --- |
| 编辑值为 `"字" * 199 + "\n"` | Python 字符数 200，UTF-16 单元数也为 200 |
| 按原生表单的 CRLF 换行形式提交 `"字" * 199 + "\r\n"` | 服务端字符数 201；POST 返回 400，提示「事项应为 1 到 200 字」 |
| 读取上述失败后的 SQLite | 旧标题、id、done 均不变；错误页完整保留提交输入与原 id action |
| 直接由 HTTP 测试客户端提交未转换的 LF 版本 | POST 返回 303，同一 id 更新成功，done 仍为 1 |

这不是失败后数据丢失：现有回显与数据库保护在该场景仍正常。问题是用户在编辑框内输入的边界标题与服务端接受条件不一致。

现有 `tests/test_app.py:272` 的 `test_edit_accepts_boundary_lengths_and_preserves_original_text` 同时测了 200 个汉字和短换行标题，但未将换行与 200 字边界组合。测试客户端直接 `urlencode(data)`，不会替浏览器验证控件值到原生表单请求的转换，因此 23 项通过没有覆盖此缺口。

**验证边界：**本次确认的是固定实现接受 LF、拒绝等价 CRLF 边界的真实 HTTP / SQLite 行为；并未实际操作浏览器输入这条边界标题。原生浏览器提交的最终复现应由主代理补充，不能把上表写成已经完成的浏览器验收。

## 建议的唯一继续目标

继续现有 BOOTV2-1：让编辑标题的长度校验与浏览器实际提交保持一致，覆盖换行边界及失败后原事项重试。仍只修改 `app.py` 和 `tests/test_app.py`，不重写事项应用、不改部署配置、不添加客户确认或签收记录。

建议执行顺序及完成条件：

1. 用实际浏览器打开隔离的固定候选，输入 199 个汉字和一个换行，通过页面「保存」提交，确认请求与失败；先固化失败复现。
2. 修正计数口径。为了校验而等价处理换行，不应擅自截断标题、改写已保存原文、删除现有测试或扩大传输上限。既有空白、CSRF、id 与故障处理仍必须成立。
3. 用真实 HTTP / SQLite 测试覆盖等价 LF/CRLF 边界、真实超长拒绝、id/done/其他事项不变、刷新及服务重启，以及数据库故障后的同一目标重试。
4. 再以原生浏览器保存和重试；确认没有出现「界面允许输入、服务端仅因表单换行编码而拒绝」的差异。Unicode 补充平面字符也属于同一计数口径的验证点，但本次尚未对其做浏览器复现，不列为已证实的新缺陷。
5. 保留现有 23 项测试并执行完整应用测试。只有这条边界实际修复并完成验证后，才记录技术改善；不能把测试数量或一次模型退出 0 当作修对率。
