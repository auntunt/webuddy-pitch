# 软件全周期 RSI：官方研究与项目落点

核验日：2026-10-18。以下区分官方结论与本项目建议；建议尚不代表已经实现。仅使用官方来源，正文按来源保持短摘要，不复制文章或技能全文。

## 1. 先定义完整产品结果，再让长任务逐步实现

Anthropic 将规划、生成、独立评估分开：规划补齐产品范围，评估操作真实应用，按可测试行为指出缺陷。模型升级后，应重新验证拆分、重置等辅助机制是否仍有必要。

- 来源：[Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)，2026-03-24；核验于本次研究。
- 项目落点：在 `intake.py` / `epic.py` 的整体目标、保留项、验收条件之上，补齐从新项目初始化到预览、交付的用户旅程；`orchestra.py` 执行，`signoff.py` 收集逐条证据。每轮 RSI 应交付一条可操作的完整路径。
- 限制：规格需要明确假设；不预先锁死所有实现细节，也不把文章中的迭代次数当固定配额。

## 2. 用实际结果评估进步，分开能力探索与回归保护

Anthropic 建议从真实失败建立评测，检查最终环境状态，混合确定性检查、校准后的模型评审和人工抽查。新能力评测与已有能力回归应分开；正反例、重复试验及干净环境能揭示偶然成功。

- 来源：[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)，2026-01-09；核验于本次研究。
- 项目落点：`learn.py:987` 当前只让 agent 生成计划，`score()` 评命中文件的 precision/recall。保留该定位指标，另建实际修改、构建测试、浏览器业务操作及最终数据断言的评测；成功案例进入回归集。记录失败阶段、首轮通过率和成本。
- 限制：文件命中不能证明修复成功；评估器也须用已知好坏样例校准，避免只接受与参考补丁相同的实现。

## 3. 持续工作依靠可恢复记录与按需知识

Anthropic 将持久会话、可替换的执行循环、执行环境分离；Skills 用简短入口按需加载流程、参考和脚本，并从实际能力缺口开始验证。

- 近期来源：[Scaling Managed Agents](https://www.anthropic.com/engineering/managed-agents)，2026-04-08。
- 经典来源：[Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)，2025-10-16，正文标注 2025-12-18 开放标准更新。两者均在本次核验。
- 项目落点：让既有 ticket/run/event、提交和证据成为恢复依据；每轮记录目标、结果、下一步与失败原因。把重复出现的需求澄清、初始化、测试、交付经验放进现有 `skills/`，确定性动作使用脚本。中断恢复先核对实际工作状态。
- 限制：优先复用 `store`、`orchestra` 和 worktree；这些原则不要求自建托管平台，也不要求更换模型供应商。

## 4. 大量 RSI 要优化可验收交付吞吐量

Anthropic 最新案例说明，代码产出加速后，版本控制、构建与 CI 会成为瓶颈。其自研版本控制服务针对特殊规模，文章仍认可 Git 对多数仓库的适用性。

- 来源：[Redesigning source control at Anthropic](https://www.anthropic.com/engineering/redesigning-source-control)，2026-10-13，2026-10-15 更新；正文日期已核验。
- 项目落点：围绕 `release.py`、`preview.py` 和 CI 记录每项需求的等待、执行、验证和发布时间；让验收证据绑定实际提交，检查并行改动整合后的结果。优先消除重复构建、等待和不可恢复失败。
- 限制：本仓库继续使用 Git；轮次、提交量和代理数量不能代替通过验收的业务结果，也不能以吞吐量为由省略必要验证。

## 5. 让产品判断有来源，让机械规则自动检查

Vercel 将产品设计经验组织成技能、lint 与证据评审循环。它区分用户任务、产品行为、既有实现和正式决策；用保留样例验证技能是否改善结果。

- 来源：[Teaching agents product design at Vercel](https://vercel.com/blog/teaching-agents-product-design-at-vercel)，2026-06-25；正文日期及内容已核验。
- 项目落点：为需求入口和工作台记录用户、主要任务、操作对象、后果、状态与成功信号；给重复问题保存来源及好坏例子。可靠的无障碍名称等规则可自动检查，流程取舍保留可解释判断；评测分别检查是否加载指导及是否正确应用。
- 限制：现有页面只证明曾经这样实现，不能自动成为标准；一次截图或一次评审不足以建立通用规则。规则更新沿用项目授权与评审流程。

## 6. 界面验收覆盖真实状态与操作

Vercel 的持续更新指南强调键盘、焦点、明确标签、异步反馈、错误恢复及多种数据状态；Geist 提供组件和视觉一致性的参考。

- 来源：[Web Interface Guidelines](https://vercel.com/design/guidelines)，持续更新，无固定发布日期；官方仓库 README 最近核验提交为 2026-10-05，`4ecfb9fb8d1d3b7009674869b3aaee2f904042e1`。
- 来源：[Geist introduction](https://vercel.com/geist/introduction)，无固定发布日期；2026-10-18 核验。
- 项目落点：对 `ui.py`、`ui_work.py`、`workbench.py` 实测窄屏/宽屏、键盘、空列表、运行中、失败、重试、权限与陈旧结果；从用户入口走完初始化、需求、开发、预览、验收和交付，保存截图及操作证据。
- 限制：Geist 是参考，不要求引入 React 或复制 Vercel 品牌；只覆盖产品实际可达状态。源码检查不能替代渲染和交互验收。

本轮优先顺序：打通新项目初始化与完整交付路径 → 验证真实用户行为 → 将失败固化为回归 → 再扩大并行和自动化范围。
