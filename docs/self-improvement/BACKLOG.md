## SI-001 · 客户答复后的再理解超时恢复

来源：本轮检查 `tmh/platform/intake.py` 的 `_give_up`、`_land_client` 与客户答复路径。

已确认工单的客户答复触发再次理解时，如果智能体超时，答复可能只追加到检查描述，原标准中的“待确认”占位仍在。此时问题列表已清空，`open_ac` 仍存在，自动流转无法继续。现阶段继续保守阻止开工。

验收：有稳定复现测试；答复不丢失；界面提供有效重试或工程师确认的恢复入口；恢复结果保留来源与证据；不修改已确认合同，不把未知标准默认通过，不绕过人工接管或全局关闭。

## SI-004 · 用修对率衡量学习是否有效

来源：`docs/evidence-flow.md` 与 `tmh/platform/learn.py` 的历史方向。

先核对现有经验卡、跨项目共享和对照实验实现，再选择一个可复现任务集。以完整修改后的行为与验收通过率为结果；文件命中仅作过程指标。旧代码修改前补必要的特征测试，避免仅改命中文件就被算成学习成功。

验收：对照条件明确，样本与结果可重跑；失败案例保留；没有成功证据时不提升经验可信度。

实现轮已保留一个真实案例的失败候选、修正来源，最终严格解码候选有 23 项应用测试与独立 150 次 HTTP / 495 项断言，另有第二人 76 项补充断言。旧候选 22 项测试与 138 次 HTTP / 459 项断言的记录也完整保留。断言数量仅表示覆盖量；一个案例不能推导修对率，也不能把模型退出码或采纳提交数量作为成功率。

## SI-007 · 将下游质量与安全检查绑定待验收实现（下一轮优先）

实现轮读取代码发现：交付的质量/安全只读执行仍可能读取项目主干，而实际实现留在已采纳的独立提交；签收快照还可能选择普通工单的最新方案，而非交付阶段已复核的方案。先补真实 Git 场景，固定实现提交和方案来源，运行证据改变时使旧下游结论失效。

验收：主干与候选故意有不同缺陷时，质量/安全确实检查候选；分支之后移动不改变受检对象；方案后来新增不替换已绑定方案；界面明确显示依据版本和仍未完成的客户签收。

## SI-008 · 限制真实模型修复总耗时并明确输入边界

实现轮暴露了多轮修复过长、沙箱内无法监听 TCP、模型对“任意超长输入都应恢复”的解释反复扩展实现等问题。每次调用配置 600 秒，但实际计时存在超过该值的调用；应复现进程树和标准输出管道的退出行为，再实现整个运行的总时限、取消后子进程回收与清楚的恢复入口。保留完整输入和日志，不通过截断提示或删除失败记录控制成本。

已观测到 Node 包装进程消失后，对应 `last-message-7.md` 的原生 Codex 子进程仍在 PID 1 下运行、继续占有本轮工作树和输出管道。已仅终止该次遗留进程树，原始进程列表在 `stalled-call-stop.json`。长墙钟时长可能包含主机休眠，不能把全部时长直接解释为模型计算时间。

验收：包含派生进程/持有管道的假执行器也能按时终止，未结束任务不能被当成通过；原始失败与当前代码可继续；表单合法业务长度、可恢复错误窗口、传输拒收边界在任务创建时明确。实际 TCP/浏览器验证由能访问测试环境的验证器完成，模型沙箱内替代测试单独标注。

## SI-009 · 其余已发现的证据与隔离缺口

- Python 项目的现有 impact 工具可能不支持 `.py`，空结果不能冒充“无影响”；本轮已停止在未安装工具的项目提示模型执行不存在的命令，工具覆盖本身仍待补。
- 预览健康判断目前较宽松，应检查约定的健康接口及数据库实际可用，不能仅把低于 500 的响应都算可用。
- 当前轻量项目的主干与候选预览共用稳定 SQLite 路径，数据持久性已验证，但复杂客户应用需要候选数据隔离、迁移和回滚证据。

## SI-005 · 全周期任务的实际执行器与证据覆盖

新工作台提供 12 类目标和 8 个阶段，但非代码阶段目前通过只读智能体形成产物。逐项补齐原型验收、数据迁移、性能测量、安全扫描、发布回执、回滚演练、监控告警和文档发布等实际执行能力。使用项目已有工具与明确环境；未配置的能力显示缺项。保持发布版本、启动预览、部署生产三种证据分离。

验收：每类任务至少有一个可运行场景；检查命令和结果可追溯，失败可重试，数据和权限边界明确。不要一次将所有工具装进提示词；按阶段、项目和实际需求加载。
