# 项目知识库：设计说明

## 要解决的问题

智能体维护老项目时，常见做法是每个任务都重新读一遍代码，然后再改。这样有三个问题：

- **不准**：上下文窗口装不下几十万行代码，模型只能读到一部分，结论靠猜。
- **贵**：同样的代码在每个任务里都要再读一遍，token 花在重复理解上。
- **不积累**：这次弄清楚的业务规则，下次会话又忘了，团队也看不到。

人类工程师不是这样工作的。接手项目时，他们会花时间把系统整体弄懂，把理解写成文档和脑子里的“地图”。之后每次改动只看相关部分，改完再更新自己的理解。tmh 的知识库就是把这个过程工程化：

1. **一次统一分析**：全项目分析后沉淀成知识库，包括知识图谱和 Wiki。
2. **按需取用**：每个任务先查知识库，只读相关代码。
3. **增量维护**：代码一变，就能精确算出哪些知识过期，只修订这些。

## 三层结构

```
┌──────────────────────────────── Wiki（.tmh/knowledge/，随代码提交） ────────────────────────────────┐
│ index.md 系统总览                                                                                   │
│   └ domains/<域>.md 业务域 ── flows/<流>.md 业务流 ── entities/<表>.md 业务对象                     │
│ modules/<模块>.md 代码模块    glossary / decisions / pitfalls / open-questions                     │
│ 每页 = 事实块（工具生成，带 文件:行号）+ 理解（智能体撰写、人确认）                                    │
├──────────────────────────────── 业务域划分（domains.json，可手工调整） ─────────────────────────────┤
├──────────────────────────────── 知识图谱（.tmh/cache/graph.db，可随时重建） ─────────────────────────┤
│ 节点：模块 · 文件 · 类 · 方法 · 入口(URL/定时任务/消息) · 表/存储过程 · 业务流 · 业务域 · 状态机 · 外部副作用 │
│ 边：包含 · 处理 · 调用 · 读/写(C/R/U/D/P) · 副作用 · 业务流步骤 · 使用 · 归属 · 状态转换 · 模块依赖        │
│ 每个节点有内容指纹（方法体、SQL、表结构、成员列表……）                                                   │
├──────────────────────────────── 按文件缓存的解析结果（.tmh/cache/parse.db） ───────────────────────────┤
└───────────────────────────────────────────────────────────────────────────────────────────────────┘
```

- **知识图谱**完全由工具确定性地生成，不花 token。它能识别 Spring MVC、Struts、Servlet、ASP.NET MVC/WebForms、WCF/ASMX、Quartz、@Scheduled 和消息监听，数据访问方面能识别 MyBatis XML 和注解、JDBC/ADO.NET 里的 SQL 字面量和 EF。
- **Go 项目**（有 `go.mod`）：包里的函数按“包名.函数”、结构体的方法按“包名.结构体.方法”建索引，同名包用目录区分（如 `relay/common`）；导入别名、参数类型、局部变量类型（含按被调函数的返回类型推断）都会解析，结构体满足接口的方法集就算实现了接口。入口认 gin 路由（`Group` 前缀拼接，最后一个参数是处理函数）、`net/http` 的 `HandleFunc`、cron 的 `AddFunc`，以及 `main` 和 `init` 里 `go 包.函数(...)` 起的后台协程。表认 GORM 模型（带 `gorm` 标签或嵌 `gorm.Model` 的结构体，表名取 `TableName()`，否则按 GORM 默认的蛇形复数），数据访问认 GORM 链式调用（`Model(&X{})`、`Table("x")` 或操作参数的类型决定是哪张表，`Create`/`Save`/`Update`/`Delete`/`Find` 等决定增删改查，`Update("status", …)` 记为状态变化）和原生 SQL。业务规则取 `if` 里带返回的报错（`errors.New`、`ApiError`、`c.JSON` 的 `message`）。`_test.go` 和 `vendor/` 不进图谱。
- **业务域**划分有三条规则：
  - 先按入口类所在的包或类名词干，把业务流聚成组。
  - 只有定时任务的组，或者不“拥有”任何表的组，并入它写得最多的那张表的拥有者。
  - 审批日志这类被多个域共同写入的表，不会把无关的业务粘在一起。

  划分结果写进 `domains.json`。以后重建时，已经分好的业务流保持不动，只给新的业务流分配域；人工改过的划分始终优先。
- **Wiki** 每页上半部分是事实块，每次构建自动刷新，不会和代码不一致。下半部分是业务理解，按固定的二级标题写，必须带证据。

## 锚定与过期检测

每个页面在写成时，都会记下它描述的那些图谱节点的指纹。例如一条业务流记的是入口和沿途每个方法（含 MyBatis 语句的 SQL）的指纹，一张表记的是表结构、读写它的方法清单和它的状态机。

`tmh kb build` 重建图谱后会逐页比对。指纹变了，或者多出了新的锚点，这一页就标为“过期”，并列出是哪些节点变了。实测（见测试 `test_done_validates_then_code_change_marks_only_affected_pages_stale`）：改了报销审核方法里的一行，过期的只有“财务审核”这一页，同一个类里的“出纳付款”页不受影响。

只改行号不会让页面过期，因为指纹按代码内容算。页面的业务理解和证据行号可以在下次修订时一起更新。

## 全项目分析：任务队列

全项目分析由工具生成的任务队列驱动，**自底向上**：业务流 → 业务对象 → 代码模块 → 业务域 → 总览。

- **上下文包**：`tmh kb next` 领取一个任务，同时给出这一页的写作要求和上下文包，上下文包有字符预算（默认 24,000 字符）。
  - 业务流：事实块、SQL，以及沿调用链按“入口 → 业务层 → 数据层、规则多的优先”排列的源码。
  - 业务对象：使用它的业务流的摘要、规则和状态变化。
  - 业务域、总览：下层页面的一句话摘要和关键段落。**上层页面不再读代码**，这是控制 token 的关键。
  - 修订过期页面时：旧的说明，加上变了的节点。只改受影响的段落，不用重写。
- **校验**：`tmh kb done` 检查以下几项，不通过不入库：
  - 必填的标题和摘要；
  - 每个二级标题都有内容，不是模板占位；
  - 证据 `文件:行号` 真实存在且行号不越界；
  - 业务流和业务对象页面至少有一条证据。
- **依赖与并行**：
  - 上层页面要等下层页面写完才会被派出。
  - 多个子代理（`kb-writer`）用不同的 `--who` 同时领任务，按页面加租约（30 分钟），不会重复劳动。
  - 登记表的写入有文件锁。
- **范围控制**：大项目不需要每个只读查询都写一页。
  - 默认每个业务域纳入最多 25 条业务流，按“写表 × 3 + 状态变化 × 3 + 规则数 + 外部副作用 × 2”排序，没有写操作的流不纳入。
  - 纳入的表是被业务写入的表。
  - 范围外的页面在任务需要时用 `tmh kb next --page <id>` 按需补写。
  - 可以在 `.tmh/config.json` 的 `kb` 节点调整：`max_flows_per_domain`、`all_flows`、`pack_chars`。
- **成本可见**：`tmh kb status` 显示累计投入的上下文量。每一页入库都会记进“分析过程”时间线。

## 日常任务：先查知识库

`tmh context "<需求原文>"` 的检索方式：

1. **切词**：中文按二元组切分，标识符按驼峰和下划线拆开。
2. **扩展同义词**：用 `glossary.md` 里的“业务词 ↔ 代码/表”对照扩展查询词。
3. **匹配**：在知识页和图谱节点上做 BM25 式匹配。
4. **沿图谱扩散**：命中方法时，带出经过它的业务流；命中业务流时，带出它用的表和所属的域。

输出控制在 8,000 字符左右，包括：先读哪几页（标出过期和未写的页面）、相关业务流、相关表（含写入方）、相关代码位置（文件:起止行），以及下一步建议。

AGENTS.md 里写明了“知识优先”的工作方式：任务开始先运行 `tmh context`，再打开它指出的文件。弄清了知识库里没写的东西就顺手补上。改完代码后，Stop 钩子会提醒运行 `knowledge-upkeep`，也就是 `kb build` 加上修订过期页面。

## 状态与人工确认

| 状态 | 含义 |
|---|---|
| 未分析 | 只有事实块 |
| 待确认 | 智能体写完并通过校验 |
| 已确认 | 有人看过，`tmh kb confirm <id> --by <姓名>` |
| 过期 | 描述的代码变了，等修订；修订后回到“待确认” |

智能体不能把页面标成“已确认”。

## 性能

在合成的 9.4 万行 Java 项目上实测：60 个业务域、1,500 个接口、3.5 万个方法。

| 构建 | 用时 |
|---|---|
| 首次 | 约 11 秒 |
| 没有改动时重建 | 约 8 秒，解析全部来自缓存，时间主要花在逐方法追踪调用和刷新 1,863 个页面的事实块上 |

这个环境里的 Python 3.13 是单进程运行。几十万行的真实项目预计在一分钟以内，但还没有实测。

## 已知局限

- 方法按“类名.方法名”标识，不同包下的同名类会合并；重载方法合并为一个节点。
- 反射、动态拼接的 SQL、配置驱动的路由、存储过程内部逻辑、JSP/前端脚本里的规则，静态抽取都看不到。这些会出现在“未能解析的调用”里，需要智能体在理解部分写明。
- 业务域自动划分依赖包名和类名。按层分包、命名又不规范的项目，第一次划分需要人工调整 `domains.json`。
- 检索是词法匹配，没有向量检索。业务方的说法和代码命名差别很大时，靠 `glossary.md` 补齐。
